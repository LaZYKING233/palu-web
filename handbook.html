01 / 关于AI第一章 · 关于 AI

目标：分清 LLM、Harness、Agent，并认识与校园帕鲁相关的常用语言。读完你应该能回答——模型能生成代码，为什么还需要文件、工具和验证环境？

一、LLM：生成内容的大脑

LLM（Large Language Model，大语言模型）是在大量数据上训练的模型，当前常见模型多使用 Transformer 或相关架构。生成文字时，它根据上下文逐步生成下一个 token，可以粗略理解成一小段文字，而不一定是完整的词。

这能帮助我们理解它为什么会续写、解释和生成代码，但不能把所有 AI 能力都归结为这一句话。更重要的是：生成一个看起来合理的答案，不等于已经验证答案正确。

这个区别很重要，它解释了 LLM 的两个根本特性：

  • 它不会自动掌握你的最新资料。日期、内部文件和最新 API，需要应用通过上下文、检索或工具提供给它。没有依据时，它可能编造看似合理的函数、接口或文献；使用带搜索功能的产品，则可以让它先查资料再回答。
  • 它不保证正确。精确计算、文件统计和代码行为，应交给实际工具执行并检查结果。即使解释很流畅，也不能代替验证。

不同模型和产品的能力不一样。选工具时，可以关注下面四项，而不是默认每个模型都支持：

长上下文一次可以处理较多资料，但能装下不等于已经读全或理解准确。项目仍需要有选择地检索和核对。
工具调用模型能输出「我要调用这个函数、参数是这些」的结构化请求。这是它能动手的前提。
多模态部分模型支持图像、音频或视频，具体输入类型要看所用模型与产品。
结构化输出部分接口能约束 JSON 等输出格式；格式符合要求，不代表数据准确，更不代表生成的代码能运行。
但这些能力本身还不等于「Agent」

它们是 Agent 用来做决定的大脑。一个只会想、不会动、也没有人替它兜底的大脑，还算不上能干活。

二、Harness：给大脑接上身体

一次模型调用能看到的，是运行环境提供的上下文。历史对话、记忆和文件通常由应用管理；模型可以提出工具调用，但实际读文件、执行命令和检查结果，需要外部环境完成。

把这些事组织起来的运行层，我们在这里称为 Harness。为了方便理解，可以用一句话概括：

Agent = Model + Harness

一篇 Harness 研究论文提出了四部分框架。这里用它帮助理解，不把它当作所有产品都必须遵守的行业标准：

① Agent Loop推理 → 行动 → 观察结果 → 再推理的循环。关键在「观察」：每做完一步都要拿到真实反馈，而不是一口气写完就交差。
② Tool Interface让模型能真实地感知和修改外部环境：读文件、写文件、跑命令、访问网络。没有工具，模型只能输出文字。
③ Context Management决定每一轮把哪些内容喂给模型。项目结构、历史对话、报错信息，喂得准它才答得准。
④ Control Mechanisms沙箱、权限、验证器和确定性检查，把一部分边界交给程序落实，而不只依赖模型愿意服从。它们需要与人工审查一起使用。

哪些是 Harness，哪些不是

这几个概念很容易混。看一张表就清楚了：

类别是什么例子
模型负责思考和生成Claude、GPT、Gemini、DeepSeek
Harness把模型包起来，让它能真的干活Claude Code、Codex、opencode、Hermes Agent
框架帮助开发者组织流程与运行机制，可能已包含部分 Harness 能力LangGraph、CrewAI、AutoGen

框架和 SDK 通常面向开发者，成品工具通常更适合直接使用；它们的功能可以重叠。不用靠名字判断，要看它是否已经提供文件操作、工具执行、上下文管理和权限控制。

三、Agent：跑起来的完整系统

Agent 是「模型 + Harness」组合之后跑起来的形态。给定一个目标，它自己决定下一步做什么、调哪个工具、怎么验证结果，一直干到目标完成或触发停止条件。

可以从下面几个角度理解，但这些不是互斥的产品分类：聊天产品也能使用检索和工具，Agent 也可以调用 RAG。

形态它做了什么谁在决定下一步
聊天交互根据输入回答，也可能使用工具由人发起；任务如何推进取决于产品
RAG 检索增强先检索资料，再辅助生成回答可以由固定流程或 Agent 触发
Agent检索、决策、执行、观察、再决策，循环往复模型自己

理解 Agent 的四个常见部分

Planner 规划
把大目标拆成一个个能独立完成的小目标。
Executor 执行
推进当前步骤，提出工具调用，并根据真实结果决定下一步。它可以与规划由同一个模型完成。
Memory 记忆
短期 = 上下文窗口里的对话缓冲；长期 = 向量库、结构化数据库，或者就是你硬盘上的文件。
Tools 工具
网页搜索、代码解释器、数据库查询、文件操作、API，甚至另一个 Agent。

这四部分不一定是四个独立 Agent。Anthropic 在 Building Effective Agents（2024-12）中区分了预设流程的 workflow 与运行时由模型决定推进方式的 agent：前者较容易控制，后者更灵活。RAG 则是两者都能使用的检索增强方法。

一、先回到那句话

第一章用一句话概括：Agent = Model + Harness。模型是脑子，Harness 是让它能推进任务的运行环境。

普通网页聊天通常不能任意操作你的本地硬盘，但 ChatGPT 等产品也有带搜索、文件和云端执行的工作入口。Claude Code、Codex、opencode 则可以在获得授权后读项目、改代码、执行命令并观察结果。要看具体入口和权限，不能只看产品名字。

所以这一章要回答的是：这些身体现在有多少个？分别长什么样？该选哪个？用了有什么代价？

先说结论中的结论：如果你是零基础，Claude Code 和 Codex 这两家的桌面端都很好用，图形界面、不用碰终端，二选一即可。剩下的等你有需要再看。

  • Roo Code——官方仓库说明项目于 2026-05-15 停止维护，扩展与云产品关闭，仓库已归档。
  • Windsurf——2025-07 被 Cognition 收购，当前入口转向 Devin Desktop。收购或更名不等于产品停服。
  • SWE-agent——官方仓库说明主要开发精力转向 mini-swe-agent，并建议后续使用后者；不必把两个项目当成同一个维护状态。

判断维护状态，要一起看归档标记、维护公告、近期发布和提交。最后提交时间只是一个线索，不能单独证明项目可靠或已经停服。

三、Claude Code：四种形态

Claude Code 是 Anthropic 的产品。命令行、桌面 Code、IDE 和云端都能用于编码任务，但运行位置、配置加载和可用功能有差别。同一账号能用哪些入口，要看当前套餐和部署方式。

你不必只选一种入口。可以按任务切换，但不要默认本机配置、MCP、记忆和会话会自动同步到每个环境；切换后要确认项目路径和已加载的配置。

形态 A命令行版（CLI）

在终端里运行 claude，它直接读你的文件、改文件、跑命令。装法在后面「上手」那一节有。

命令行特别适合把任务接进脚本，也可以用于远程查看和继续会话：

  • 一次性非交互模式（headless）：-p 让它跑完一个任务就退出，适合写进脚本或者 CI。 
    # 跑一次就退出
claude -p "解释这个函数在做什么"

# 限制非交互任务轮次和 API 花费；不等于所有订阅的消费上限
claude -p --max-turns 3 --max-budget-usd 5.00 "检查有没有语法错误"
  • 手机远程查看：claude remote-control 可让手机查看和回复本机会话，执行命令仍在本机；电脑和会话需要保持运行。这不代表数据完全不外发：使用云端模型时会发送所需上下文，远程控制也会同步会话。它不同于在云端运行的 Code 会话。

什么时候用命令行版：写脚本、进入 CI 或在容器终端里跑任务时很方便。SSH 不必只用 CLI，桌面端也支持远程 SSH 环境；选自己顺手、且符合项目权限的入口即可。

形态 B桌面端（Code 标签）

很多人以为「Claude Code 只是个命令行工具」，这是误解。它有桌面应用，准确说是 Claude Desktop 里的 Code 标签页——同一个应用里有三个标签：Chat（普通聊天）、Cowork（长时间的自主任务）、Code（写代码，你要找的在这个里）。

最关键的一点：桌面端能直接读写你电脑上的项目文件，不是只能生成代码让你复制粘贴。选一个 Environment（Local / Cloud / SSH / WSL），指定项目文件夹，它就在真实的环境里干活。

它比命令行版多了这些图形化能力：

Diff 审阅改动逐个文件显示，可以点某一行直接写评论，它读到评论再去改。这是命令行版没有的。
内置终端和 Claude 共享同一环境，跑 npm test 看到的是同一批文件。
文件编辑器点路径直接改、保存回磁盘。
分屏布局对话、diff、终端、浏览器、文件任意拖拽排列，还能弹成独立窗口。多任务并行时很关键。

会话能不能在两端接着聊？能，但要注意规则：两边共享 CLAUDE.md、MCP、Skills、设置这些配置，但各自维护自己的会话列表。会话可以用 /desktop 从命令行搬进桌面端，也能从桌面端捡回命令行——搬的是同一个会话，不是副本。

桌面端的边界：没有 CLI 的 -p 非交互入口，因此脚本和 CI 仍适合用 CLI。桌面端默认连接 Anthropic，但官方也提供 gateway 和第三方部署路径；不能把“默认”理解成“只能”。参见桌面端说明。

什么时候用桌面端：你不想碰终端、想一次开几个任务并行做、想图形化看 diff。这三种情况它明显比命令行版舒服。零基础强烈建议从桌面端开始。

形态 CIDE 插件（VS Code / JetBrains）

在编辑器里直接用。VS Code 上它是官方推荐的方式：内联 diff、计划审查、用 @ 引用你选中的几行、能翻历史会话。适合「我本来就整天开着 VS Code 写代码」的人。

形态 D云端（claude.ai/code）

跑在 Anthropic 的服务器上，关掉本地电脑也在跑。适合长任务。代价是它看不到你本地的东西——你得把项目传上去，而且它在上面也用不了你本地的 MCP 和工具。

四、Codex：同样四种形态

Codex 是 OpenAI 的产品，CLI 部分是完全开源的（Apache-2.0 协议，仓库在 github.com/openai/codex，用 Rust 写的）。这一点和 Claude Code 正好相反，值得知道。

Codex 的常见入口包括 CLI、ChatGPT 桌面端中的 Codex、云端和 IDE 集成。项目可用 AGENTS.md 提供说明，但各环境仍要确认说明文件、权限和登录方式，不能默认配置都已同步。[官方快速入门]

形态 ACodex CLI（命令行）

装好后在项目目录运行 codex。下面是 CLI 用法；参数以当前版本帮助与非交互文档为准：

  • codex exec——跑一次就退出，进度走 stderr，只有最终结果走 stdout，写脚本用这个。 
    codex exec "解释这个项目的文件结构，不修改文件"

# 沙箱默认只读，要写文件得显式放开
codex exec --sandbox workspace-write "修复测试失败"

# 结构化输出示意：先准备好定义输出格式的 schema.json
codex exec --output-schema schema.json "用实际统计工具统计代码行数，按 schema 输出"
  • codex review——非交互式代码审查。可以针对未提交的改动、某个 commit、或者和某个分支的差异。

新手最该记的斜杠命令：/init（生成 AGENTS.md）、/plan（先出方案再动手）、/review（审查改动）、/permissions（设权限）、/status（看状态）。

形态 BChatGPT 桌面端里的 Codex

桌面端提供图形化的 Codex 工作入口，可以选择项目文件夹、审阅 diff 和查看任务。它不是把普通聊天框换个名字，而是使用获授权的文件和开发工具。

项目与会话
Codex 有自己的项目和会话入口，不要默认普通 ChatGPT 对话里的文件与上下文已经提供给它。
跨设备查看
远程入口可以查看受支持的会话，但要核对会话运行在哪、如何同步，不必把所有入口当成同一份聊天记录。
本地工作
选择本地项目后，可以在权限允许的范围内使用文件、仓库、终端和开发工具。

不同版本的应用名称和界面可能变化。安装与入口以官方桌面端说明为准；需要跨设备操作时，再查看Remote 说明。

什么时候用这个形态：你已经有 ChatGPT 订阅，想在一个图形界面里审 diff、同时盯几个任务，不想再装别的软件。

形态 CCodex Cloud（云端）

任务运行在云端环境时，不依赖你本机一直开着。通常先选择仓库并配置环境，再启动任务；依赖能否安装、测试能否执行，要看实际配置，不能把开出任务当成完成验证。

适合电脑要关机或希望使用独立云端环境的任务。Codex Cloud 要用 ChatGPT 账号登录，不能用 API key 代替；套餐权限、用量和开放范围查认证说明及当前权益。私有服务凭据只配置最小必要权限。

形态 DIDE 插件

VS Code 及兼容编辑器使用 Codex 扩展；Xcode 和 JetBrains 有各自的集成入口，不是同一个插件。引用文件、审阅改动和云端任务等能力也要看具体入口。参见官方 IDE 说明。

一个好消息：AGENTS.md 两边都能用

Claude Code 从 v2.1.277 起支持直接读取 AGENTS.md，但默认选择还受当前目录及上级目录的 CLAUDE.md / CLAUDE.local.md 影响，也可以配置为同时读取。团队可以统一维护说明，不必强制所有人删除另一类文件。

还要检查版本、内置插件和会话设置；部分旧版或升级后的首次会话有例外。先确认当前会话确实加载了团队规则，再工作。具体以Claude 加载规则和Codex 加载规则为准。

五、其他几个值得知道的

除了上面两家主流的，还有几个在开源社区里很活跃的工具。了解它们有助于你看懂这个领域，但零基础暂时不用装。

opencode模型无关的开源 Harness

一句话：一个支持多家模型服务和本地模型的开源 Harness，选择前先确认想用的接口是否兼容。

它不只面向一家模型服务商，可以配置兼容的服务端点，也能使用本地模型。当前支持范围、安装与许可查 Anomaly 的 opencode 官方仓库，不要把“模型无关”理解成所有模型都能无配置接入。

形态是终端界面（TUI）+ 桌面端 + 常见 IDE 的插件 + 网页版。它的规则文件也叫 AGENTS.md（同时兼容读取 CLAUDE.md）。

适合谁：想自由切换模型、或者想在同一个工具里同时用好几家模型的人。代价：你要自己准备 API key 并配置，开箱即用性不如订阅制产品。

注意名称：这里指 Anomaly 的 opencode，不是 OpenAI 的 Codex。搜索时同时核对开发者和仓库地址，避免装到同名项目。

Hermes Agent会自己沉淀经验的常驻助手

Hermes Agent 不是模型，是智能体运行工具。Nous Research 的 Hermes 模型与 Hermes Agent 是不同层面的产品；Agent 可以连接受支持的其他模型，不必只使用同名模型。

它强调把经验沉淀为技能、记忆和用户资料，在后续任务中复用。这主要是保存和组织上下文，不等于自动修改模型权重。持续记忆不是它独有的能力，例如 Claude Code 也有自动记忆。

它可以自部署，并通过 gateway 接入多种通信平台；支持清单和部署条件以 Hermes 官方仓库为准。

适合谁：想要一个长期在线、能从手机各个 App 找到的个人助手。不适合：只想安静写代码的人——它比纯 coding agent 重得多。

一个正好能说明「Harness ≠ 模型」的例子

模型与工具需要搭配：要看模型的工具调用能力、接口兼容性和实际任务表现，而不是名字相同就默认最好用。选择后先用低风险任务验证，不要直接接真实账号和服务器。

DSHDeepSeek 官方的开源 Harness

DSH 是 DeepSeek 官方的开源 agent 工具，仓库是 deepseek-ai/deepseek-harness。项目强调插件化；当前功能、许可和运行入口以仓库说明为准。

DSH 是运行工具，不是 DeepSeek 模型本身。它可以配置受支持的模型服务或兼容端点；能否接入某个模型，要核对提供方、协议和具体配置，不是填入任意 API key 就保证能用。

重要提醒：截至 2026-10-02，官方仍将它标为 developer preview，可能有破坏性变更。安全说明明确表示未经过安全审计，不能当作安全或生产就绪软件。不要给试验环境真实密钥或重要数据。

适合谁：想研究 agent 架构、想写插件、想用第三方模型跑 coding agent 的开发者。不适合：日常写代码，更不要用在生产环境。

按你的情况对号入座：

在服务器 / 容器 / SSH 上干活CLI 很方便；支持 SSH 的桌面入口也是选择之一

「本地运行」这个词有歧义，务必分清两层：

  • Harness 跑在哪——比如 Claude Code 桌面端选 Local 模式，程序跑在你电脑上。
  • 模型跑在哪——连接云端模型时，提供给模型的代码上下文和工具结果可能发送到服务商，不代表整份仓库都会上传。

本地模型可以减少模型请求外发，但还要检查插件、遥测、网页请求和远程服务，不能只看“本地”两个字就保证完全离线。使用同学资料或内部代码前，先确认授权和数据流向；不要把密码交给模型。

七、装一个并跑起来

下面演示 CLI 的安装，不代表新人必须先用终端。只选自己要用的一种工具；桌面端可先看官方入门。安装命令核对于 2026-10-02，运行前确认来源是Claude 官方或Codex 官方。

# macOS / Linux / WSL
curl -fsSL https://claude.ai/install.sh | bash

# Windows（PowerShell）
irm https://claude.ai/install.ps1 | iex

# 装完先确认
claude --version

第一次用，按这四步走：

  1. 进到正确的项目目录再启动。先 cd，再运行 claude。工作目录不等于安全隔离：能读写哪些目录仍取决于权限、额外目录和沙箱设置。

    cd ~/projects/my-app
claude

  2. 可能会询问是否信任这个文件夹。先核对来源与路径；不熟悉的仓库不要盲目信任，也不要直接执行其中的安装或自动化脚本。

  3. 先问，别先改。刚进一个新项目，先让它自己介绍自己。

    这个项目是做什么的？用了什么技术栈？

  4. 退出用 /exit。或者在空提示符下连按两次 Ctrl+D。

那 Codex 怎么装

# macOS / Linux（官方推荐）
curl -fsSL https://chatgpt.com/codex/install.sh | sh

# Windows（PowerShell）
powershell -ExecutionPolicy ByPass -c "irm https://chatgpt.com/codex/install.ps1 | iex"

# 登录：推荐用 ChatGPT 账号，不用单独买 API key
codex login

# 然后照旧 cd 到项目里再运行
cd ~/projects/my-app
codex

若提示找不到 codex，先确认安装成功、重启终端并检查 PATH；改成 codex login 并不能解决命令不存在。CLI 首次启动会引导选择登录方式。

一个真实的坑：别装错包

若使用 npm，OpenAI 的包名是 npm install -g @openai/codex，不要省略 @openai/。同名包不一定是同一个产品，装完还要核对来源和版本，不能仅凭命令能执行就判断正确。

八、权限：重要的安全带

你每次看到它问「是否允许执行 xxx」，那是在问你：你允许我动你的电脑吗？

允许执行命令之前，要看清它会读写什么、是否联网、会不会影响真实服务。人工确认、沙箱、最小权限、密钥管理和备份需要一起用；任何一层都不能单独保证安全。

以下以 Claude Code 为例，常用切换键是 Shift+Tab。可用模式和行为随版本、配置变化；其他工具的审批与沙箱不要照搬。参见官方权限说明。

模式它能做什么什么时候用
plan以只读分析和制定计划为主，不直接实施修改不确定影响范围时
acceptEdits自动批准文件编辑和部分常见操作；其他操作仍受权限规则约束确认方案后
default需要批准的操作会询问；已有允许规则的操作可能直接执行处理不熟悉的仓库时
跳过审批绕过权限询问，不等于移除所有其他限制新手不要使用
新手不要跳过权限

--dangerously-skip-permissions 会跳过审批。不要在有重要文件、真实凭据或生产访问权的环境里试。即使用一次性容器，也要检查挂载目录、网络和凭据：容器能访问到的东西，仍可能受影响。

九、给它写一份项目说明书

把项目说明写进工具支持的 Markdown 文件，可以减少重复解释。是否加载、目录范围及个人配置的合并方式，要看工具和版本；说明文件不是强制安全机制。提交到仓库后，团队才能共享规则。

工具文件名作用范围
Claude CodeCLAUDE.md 或 AGENTS.md当前项目，随仓库提交
CodexAGENTS.md当前项目，随仓库提交
opencodeAGENTS.md当前项目，随仓库提交
Claude Code~/.claude/CLAUDE.md你自己的所有项目
Codex~/.codex/AGENTS.md你自己的所有项目

可以让工具扫描仓库，再核对生成的说明。Claude Code 的 /init 通常生成 CLAUDE.md；Codex 使用 AGENTS.md。下面以我们这个静态官网为例，不套用不存在的 npm 脚本：

# AGENTS.md

## 怎么预览
- 静态官网，不需要 npm install。
- 浏览器打开 index.html，或使用已有的静态服务器。
- 检查链接、桌面与手机排版、手机菜单展开。

## 约定
- 只改任务指定的文件，保留已有视觉风格。
- 不提交密钥、账号密码或真实用户数据。
- 暂存前逐个核对文件；没有授权，不提交或推送。
写说明书的两条原则

第一，写可验证的事实，少写形容词。第二，保持精简，但不存在所有工具统一的 200 行截断规则。Claude 的自动记忆入口上限不能与项目说明混为一谈；Codex 的项目说明默认有 32 KiB 合并上限，可配置。长流程可拆成 Skill。见Claude 记忆说明与Codex 项目说明。

另一个能力是在独立工作树里干活。它能分开不同分支的文件改动，但不隔离共享数据库、端口、外部服务或部署环境。以 Claude Code 为例：

claude --worktree feature-login

文件会放在 .claude/worktrees/feature-login/。适合「让 AI 改 A 功能，你同时改 B 功能」这种并行场景。团队多人同时开发时也建议这么干。

十、Harness 的优缺点

前面九节都在讲怎么用。但这一节更重要——任何工具都有代价，你得知道付的是什么。

它确实很强的地方

  • 从「能聊天」到「能干活」的质变。这是最实在的一条。以前 AI 只能给一段代码让你复制粘贴，现在它能自己读文件、跑起来、看报错、再改——反馈闭环是质变，不是效率提升。
  • 上手门槛低到反常。会说话就能用。你不需要会写代码才能让 AI 写代码。
  • 能跨文件理解任务。长上下文和检索工具让它有机会结合相关代码分析，但不意味着它读完了仓库或理解一定正确。让它列出依据和读过的文件，仍然很有用。
  • 版本记录降低试错成本。Git 能恢复已经记录的代码；未提交、被忽略的文件，以及数据库和外部服务的变化，不能靠一次回退全部恢复。
  • 生态提供更多协作方式。Skill、MCP 和插件可以复用流程、连接工具，但兼容性和维护状态要逐项核对。

必须知道的缺陷

一、安全问题有实证数据，不是空谈

一项对 200 个已部署 AI 生成应用的审计发现，样本中 91% 至少有一个漏洞；检出的 1,186 个漏洞里，65.77% 为严重或高危。另一项 SUSVIBES 基准中，SWE-agent 配合 Claude 4 Sonnet 在 186 个任务上的功能通过率为 57%，同时通过功能与安全检查的比例为 11.8%。这是特定样本和设置的结果，不是所有 AI 代码的通用失败率。见应用审计与SUSVIBES。

功能可用不等于安全。安全提示和更严格的流程可能有帮助，但不能替代权限检查、安全测试和人工审查。

  • 二、修复报错时可能引入安全问题。应用审计记录了为了完成任务而放松校验或权限的情况。不能据此断言 AI 总是绕过问题、而人不会；要检查认证、访问控制和数据处理边界有没有改变。
  • 三、代码可能超出你的理解范围。这是最隐蔽的风险。Karpathy 提出「vibe coding」时就明说了这一点：代码增长到了自己理解不了的程度。代码能跑 ≠ 你能维护它。一旦三个月后出 bug，你连从哪里开始查都不知道。
  • 四、额度和费用需要确认。产品、套餐和账号限制不同，不能统一说成「每 5 小时」。订阅与 API 也可能分开计费；看清登录方式和账单。预算提醒未必是硬性停机上限，长任务还要限制循环与调用量。以Codex 当前说明为准。
  • 五、云端能力依赖网络和服务。故障、限流或产品调整会影响工作。部分流程能迁移，但配置、权限和功能未必兼容；本地执行也不代表没有数据发送到云端。
  • 六、模糊需求容易变成猜测。AI 有时会追问，也可能直接实现自己的理解。先说清目标和验收标准，并要求「遇到影响范围或权限不明的地方，先问我」。
  • 七、工具状态会变化。预览版可能有破坏性变更，成熟项目也可能停止维护。一起看官方公告、发布记录、兼容性与安全说明，不要只凭「新」或「大厂」判断。

怎么用才能扬长避短

四个原则
  • 从出错代价低的任务开始。个人小工具、探索性原型或有备份的练习项目；一次性脚本也别直接处理重要数据。
  • 权限从紧开始。先只读分析，再批准明确的修改范围。真实账号、生产环境和联网操作单独确认。
  • 不要只让它生成代码。还要实际运行、写合适的测试、检查行为、审查 diff。测试通过只是证据之一，不是全面正确的证明。
  • 每个任务前后建 Git 检查点。这不是可选项，是让「大胆试」这个动作成立的前提。详见第六章。

十一、常见坑

  • 只看最后一次提交来选工具。还要看是否归档、维护公告、发布记录和关键问题的处理情况。
  • npm 装错包。见前面 Codex 那节的警告。
  • 在错误目录启动。先确认仓库和分支；当前目录是工作起点，不是访问边界。
  • 一个会话塞进太多任务。长会话可能压缩或遗漏细节。阶段性重述目标、约束与进度；换任务时带着摘要开新会话。
  • 以为规则文件写了就生效。写进工具支持的项目说明，再确认会话加载了正确文件。
  • 用 DSH 这类预览版做正式项目。它没经过安全审计。
04 / SKILL·MCP第四章 · Skill 与 MCP：给它装上手脚

目标：分清 Skill 和 MCP 到底是什么、各自解决什么问题，以及什么时候真的需要它们。

先分清这两样东西

这是最容易混的一对。用一句话区分：

Skill 是「经验」把任务说明、步骤和可选脚本、资料打包起来，帮助 AI 按流程工作。它不改变模型本身，但可以调用已有工具。
MCP 是「接口协议」让客户端以统一方式连接工具和数据源。它不是访问外部系统的唯一办法，也不会自动授予权限。

例如，发版后写公告的步骤与格式可以做成 Skill；读取工单系统可以通过 MCP 接口，也可以用已有 API 或客户端工具。两者能配合使用，但不是一回事。

Skill：把重复说的话存起来

如果你发现自己每次都要给 AI 贴同一段说明，或者每次都重复同一套步骤，那就该做成一个 Skill。

一个 Skill 通常是含 SKILL.md 的文件夹，可以附带脚本和资料。先以 Claude Code 的个人目录为例：

~/.claude/skills/summarize-changes/SKILL.md

Claude Code 的项目目录是 .claude/skills/<名字>/SKILL.md；Codex 使用 .agents/skills/<名字>/SKILL.md 等约定目录。不要假定同一目录能被所有工具自动发现。见Claude Skills与Codex Skills。

最小可用的内容长这样：

---
name: summarize-changes
description: 当用户要总结未提交改动或审阅 diff 时使用，只读检查改动与风险。
---

## 要求
先运行 git status --short，区分已跟踪改动与未跟踪文件。
再检查 git diff 和 git diff --cached；按需读取新文件。
用两三句话总结，列出风险和实际做过的检查。
不要把 diff 为空当成没有新文件。
不要暂存、提交或推送。

有两处值得注意：

  • name 和 description 是 Agent Skills 标准要求的元数据。名字与目录保持一致，描述清楚适用任务；是否自动选中还取决于客户端。
  • 正文是工作说明，不会自行执行命令。AI 必须在权限允许时真正运行检查并读取结果；某些客户端的动态注入语法，不要当作通用标准。

可以让客户端按任务选择，也可以明确调用。Claude Code 常用 /summarize-changes；Codex 可用 $summarize-changes。可用入口以当前客户端帮助为准。

什么时候该做 Skill

同一段说明反复出现时，就值得考虑做成 Skill。「第三次就存起来」只是经验法则；复杂的一次性流程也可能值得整理，简单任务则不必过度配置。

MCP：接上外部世界

MCP 全称 Model Context Protocol，是连接 AI 客户端与工具、数据源的开放协议。可以把它类比为统一插口，但不是插上就必然能用：仍要匹配传输方式、客户端支持、认证与权限。见协议说明。

它的结构长这样：

   你 / AI
      │
      ▼
┌──────────────┐   JSON-RPC   ┌──────────────┐
│  MCP Client  │ ◄──────────► │  MCP Server  │
│ (Claude Code)│              │ (提供工具)    │
└──────────────┘              └──────────────┘
                                    │
                                    ▼
                            数据库 / API / 文档

Server 那头会提供三类东西：

类型是什么类比
Tools可以执行的函数，比如「查数据库」「发消息」手
Resources可读取的数据资源；如何引用取决于客户端眼睛
Prompts可选的提示模板；展示与调用方式取决于客户端剧本

下面是 Claude Code 专用命令，不是 Codex 的配置语法。HTTP 示例使用 Notion 服务，需按提示认证；stdio 示例会通过 npx 运行程序，确认来源后再安装。参数中的 -- 用来分隔 server 启动命令。见官方配置说明。

# 本地 stdio server（MCP 参考实现，用于学习）

不要把旧参考实现清单当成仍在维护的官方服务。部分 Drive、Slack、GitHub、Postgres 参考实现已归档；选用前检查供应方和维护状态。参见MCP 参考实现仓库。Claude 的 --scope project 可共享配置，但不要把真实密钥写进仓库；个人配置、环境变量或认证流程要按具体服务说明设置。

大部分人其实不需要 MCP

先看客户端现有能力是否够用。文件、终端、搜索等能力的可用性也受产品和配置限制。等真正需要连接一个现有工具接触不到的系统时，再评估 MCP，减少不必要的配置和风险。

安全问题

服务端及本地启动的进程能接触到哪些数据，取决于账号权限、凭据和运行环境。先只给最小必要权限；读到的外部内容也可能包含误导性指令，不能据此越权操作。

本章要点

  • Skill 复用任务流程与资料，MCP 统一工具和数据接口；它们可以配合使用。
  • 重复或复杂的流程值得整理成 Skill，「第三次」只是经验法则。
  • MCP 等真正需要时再装。原生能力已经能覆盖大多数场景。
05 / PROMPT第五章 · 提示词：怎么把话说清楚

目标：掌握一套可重复使用的写法，减少遗漏与误解；它能改善沟通，但不能保证每次输出都正确。

同一句话，效果可以差很远

这是新手最常见的困惑：明明我说了要干什么，它怎么还是做错？

原因通常不是模型笨，而是你省略了你自己脑子里默认存在、但没写出来的信息。你说「帮我加个搜索框」，它面对的是几百种可能——搜什么字段、放在哪、什么样式、搜不到显示什么、要不要防抖。这些你都没说，它只能猜。

提示词的本质不是「把话说得客气点」，而是把你脑子里的上下文补齐，让它不用猜。

四要素：目标、背景、约束、完成标准

结合官方关于明确指令、提供上下文和示例的建议，本文整理成这四项，方便新成员使用；不是某一家规定的唯一框架。参见OpenAI 提示词指南。

目标 Goal要什么。做成之后用户能做什么。
背景 Context在哪做。哪些文件、哪段报错、什么技术栈。
约束 Constraints怎么算符合要求。风格、不能动什么、安全要求。
完成标准 Done when怎么验证做完了。可检查的条件，而不是「做好了」。

同一个需求，两种写法。下面是虚构的课程搜索练习，courses.js 不是本官网现有的数据文件：

不够好的写法

帮我给首页加个搜索框

加上四要素

目标：首页加一个课程搜索框。
背景：在 index.html 的 hero 下方，课程数据来自 courses.js。
约束：沿用现有 lilac 配色，不引入新依赖。
完成：输入即过滤，无结果显示「没有匹配的课程」。

右边把关键条件写清楚，更容易检查结果、减少返工；仍要运行和核对，不能保证一次完成。

比「一句话需求」更好用的三个做法

  • 让它反过来问你。需求模糊时，别硬凑成一句长的。直接说「先别动手。问我几个问题，把需求问清楚再来做」。它问你答，五分钟胜过猜半小时。
  • 一次只推进一小步。「先把这个改完，跑起来给我看」比「把这个项目重写一遍」成功率高得多。做完一步看一步，方向不对时损失还很小。
  • 不认可就直说，别含糊。「不太对」对它是无效输入。说清楚哪里不对：「按钮位置不对，应该在搜索框右边而不是下面」。

长期规则别塞进提示词

长期有效的项目约定，写进第三章讲的项目说明文件，并确认工具已加载。提示词负责这次任务的目标与例外；文件里的约定不等于强制权限限制，也不能覆盖真实的安全边界。

Claude Code 的 /clear 可重新开始会话，/compact 可压缩上下文；其他工具以自身帮助为准。压缩不是无损存档，先记录目标、约束、已完成内容和待办。

一个必须纠正的误解

明确安全要求，但不要把提示词当保证

SUSVIBES 的特定配置中，安全提示让功能与安全同时通过的比例从 11.8% 升到 14.5% 或 15.1%，但仍较低，并伴随功能通过率变化。不能说提示「完全没用」，更不能说一句提示就够了。见论文实验结果。

明确认证、权限和数据要求，再做针对性测试与人工审查。第六章的 Git 可以记录代码变化，但不能检查代码是否安全，也不能恢复所有外部影响。

别指望一次说对

可以把协作过程类比为带一个不了解项目的新成员：给上下文、示例和反馈。但 AI 可能误解，也可能自信地给出错误结果。要求它说明不确定处，并用实际证据核对，不把语气当作可靠性。

所以：给上下文、给例子、给反馈、随时纠偏。这是把工作做好的流程，不是话术。

06 / GIT·GITHUB第六章 · Git 与 GitHub：团队的公共记忆

目标：先学 Git 如何记录、比较和协作管理代码，再学 GitHub 的评审、检查与交接流程。Git 不只用于本地，GitHub 也不是唯一托管平台；这里用它们组成一套入门示例。

第一部分 · Git：你电脑上的版本控制

五个概念，够用了

仓库 repository
Git 跟踪的文件与版本历史。不等于目录里的每一个文件都已存档；浅克隆还可能只有部分历史。
提交 commit
一次存档点。记录改了哪些文件、改成什么样、谁改的、为什么改。
暂存区 staging
提交前的草稿区。git add 放进来，git commit 才正式存档。可以只提交一部分改动。
分支 branch
一条平行的时间线。开一条分支改东西，不影响主线；改完再合回去。主线通常叫 main。
远程 remote
另一个仓库的地址，可以在 GitHub、其他平台或自建服务器上。常见名称是 origin，但不是固定规则。

日常够用的命令

先熟悉下面这些常用命令。示例中的文件、分支和远程名称要替换成实际值；执行修改类命令前先看 git status。

命令干什么
git clone <地址>克隆仓库；是否包含完整历史取决于克隆选项
git status看现在改了什么、在哪个分支。不确定时就先敲这条
git add <文件>暂存指定文件；git add . 涉及当前目录及子目录，新手优先明确指定路径
git commit -m "说明"把暂存区的内容正式存档
git log看历史记录
git diff / git diff --cached分别看未暂存 / 已暂存改动；新文件还要结合 status 检查
git switch -c <名字>新建一条分支并切过去
git switch <分支>切到已有分支
git fetch origin下载远端对象、更新相关引用；通常不修改工作目录文件
git pull获取并整合更新；merge、rebase 或仅快进取决于参数和配置
git push把你的提交上传到远程
git restore <文件>默认用暂存区内容恢复工作文件，会丢弃该文件未暂存的改动，先确认
git branch -d <名字>删掉已经合并完的本地分支

fetch、merge、rebase、pull 到底什么区别

记成两步更准确：fetch 获取更新但不整合进当前工作树；merge / rebase 才做整合。pull 把获取与整合连起来，策略要看参数和配置。

命令它做了什么会改我的文件吗
git fetch origin获取配置范围内的远端提交并更新远程跟踪引用，不只 main通常不改工作目录
git merge origin/main整合到当前分支；可能快进，也可能产生合并提交可能会
git rebase origin/main把你的提交摘下来重放到最新主线之上，提交 ID 会变会
git pull --no-rebase origin mainfetch 后按 merge 方式整合，仍受快进等选项影响可能会
git pull --rebase origin main= fetch + rebase会

怎么选：

  • 「我想知道队友更新了什么，但不想动我的代码」→ git fetch origin，然后 git log HEAD..origin/main 看差异
  • 「把我这条分支更新到最新主线」，只有我在用这条分支→ git rebase origin/main，历史干净
  • 「把我这条分支更新到最新主线」，别人也在用这条分支→ git merge origin/main，不要改写别人的提交
  • 「让本地 main 追上远端」→ 先确认工作目录干净，切到 main，再运行 git pull --ff-only origin main。如果历史分叉而被拒绝，先找负责人确认，不要强推。
rebase 的黄金法则

不要擅自 rebase 已发布且有人依赖的历史。需要重写时先与协作者确认。自己的分支也可能已被别人使用；新手可优先用 merge 同步，不把「自己创建」当作重写授权。

.gitignore 告诉 Git 哪些尚未跟踪的文件通常应忽略。已经跟踪或提交过的文件不会因此自动移除，历史里的密钥也不会消失。下面只是通用示例，要按项目调整。见官方说明。

node_modules/
dist/
.env
*.log
.DS_Store
.vscode/

最关键的是 .env 和各类密钥文件。带密码的代码一旦推到公开仓库，等于公开发布了，后面会讲怎么处理。

第二部分 · GitHub：团队的公共记忆

Git 本身支持版本历史和多人协作。GitHub 在此基础上提供托管、issue、PR、权限和自动检查。我们用这些机制回答：谁来审、怎样验证、如何交接，以及错误发生后怎样处理。

为什么在 AI 时代反而更需要它

一个反直觉但很重要的事实：AI 让「写代码」变便宜了，于是「验证代码、归属责任、传递上下文、撤回错误」这四件事的相对成本上升了。GitHub 恰好就是这四件事的载体。

① 上下文不熟悉项目约定是常见风险。README、项目说明和 CODEOWNERS 可以记录用途、流程与责任分工；但要维护内容，并确认工具如何读取。
② 可审计GitHub 2026 年 5 月的一篇文章称，超过五分之一的代码评审涉及 agent。生成速度变快，仍需审查依据、运行结果和责任人；这里不把平台数据当作我们项目的统计。见原文。
③ 回滚分支与提交能降低代码试错成本，但不能恢复数据库或外部操作。未提交改动可能跟随切换分支；不能把「删掉分支」当成清除全部影响。
④ 交接传统项目里作者和理解者之间有天然通信链路——作者还在，微信问一句就清楚了。AI 写代码打破了这个前提：作者是 Copilot，他不在群里。PR 描述、评论线程、git blame 就是替代品。
一句话总结

本文的建议是：把 GitHub 同时当作记录依据与明确责任的地方。AI 的参与不能替代有权限的成员审查、验证和决定是否合并。

DORA 2025 把 AI 比作组织能力的「放大器」。后续官方解读指出，较高 AI 使用与吞吐量、交付不稳定性的增加都有关联；不能简单解释成 AI 必然导致不稳定。这也提醒我们，工具之外的协作与验证能力很重要。见DORA 官方解读。

机制 1Pull Request：整个协作的中枢

PR 的意思是「我改好了，请你们看一下再合并」。它不是「代码分享功能」，而是整个团队流程的中枢——评审、讨论、CI 检查、合并，全挂在它上面。

一次 PR 的完整生命周期：

  1. 开 PR（还没写完可以先开 draft，draft 不能被合并，也不会自动请求 review）

  2. 配置匹配时触发 CI；核对实际运行的检查及日志，不只看绿勾

  3. 请求评审；符合 CODEOWNERS 规则时会自动请求相应负责人

  4. Reviewer 评论 / Request changes / Approve

  5. 作者改完再提交 → 之前的 Approve 可能被自动撤销（这是故意的，防止「批准后偷偷加代码」）

  6. 所有讨论线程 resolve → 满足全部规则 → 合并

Request changes 是否阻止合并，要看规则

Comment、Approve、Request changes 是常见评审结果。启用必需评审等规则时，有相应权限的评审者要求修改可能阻止合并；并非任意评论者都能阻塞。补交修复通常不会自动解除，需要相关评审者批准，或由有权限的人按流程撤销评审。见评审说明。

关联 issue

在 PR 描述里写 Closes #12，PR 合并进默认分支时对应的 issue 会自动关闭。但有个致命限制：PR 的目标分支必须是仓库的默认分支，否则关键词会被完全忽略。也可以在 PR 右侧的 Development 面板手动关联。

机制 2分支保护：把规矩落实成检查

这是团队协作里投入产出比最高的一个设置——花 5 分钟配置，省掉后面无数麻烦。

它规定哪些条件下能更新目标分支。传统分支保护默认可能允许管理员或指定角色绕过；需要检查「Do not allow bypassing」等设置，ruleset 还要检查 bypass 列表。入口和可用功能随权限、仓库与套餐变化。见官方说明。

要勾的规则它拦住了什么
Require a pull request before merging禁止直接往 main 推代码
Require approvals（设 1）防止自己写自己批
Dismiss stale approvals when new commits are pushed防止「批准后偷偷加代码」
Require conversation resolution防止「嘴上说改了，实际没改」
Require status checks to pass要求指定检查得到可接受结果；success、skipped、neutral 可能被接受，仍须看检查是否真正运行
Require branches to be up to date要求在最新目标分支基础上通过指定检查；不证明没有逻辑冲突
Require linear history禁掉 merge commit，历史保持线性
Do not allow bypassing these settings管理员也不能开后门
Allow force pushes / Allow deletions保持关闭，这是防事故的最后一道闸

如果目标是「包括负责人也只走 PR」，就必须核对规则覆盖的分支、旁路权限和必需检查。设置存在不等于实际生效，用实际 PR 检查结果确认。

「必需检查」最容易踩的坑

检查一直等待时，核对必需检查名称、工作流事件、路径/分支过滤、运行权限和日志。配置要求的检查若未被触发，可能一直等待。不要为了消掉提示就直接删掉保护规则。

机制 3CODEOWNERS：指定代码负责人

CODEOWNERS 描述文件负责人，GitHub 可以据此自动请求评审。要让负责人批准成为合并条件，还需启用必需 code owner review，单独放这个文件不够。见官方说明。

下面是假名示例，放在 .github/CODEOWNERS。使用前替换为真实 GitHub 用户名或组织团队；负责人需有仓库写权限，团队还需满足可见性等要求：

# 以下 example-* 是占位名，不是实际成员
*                    @example-org/frontend
*.js                 @example-dev
*.css                @example-design
/docs/               @example-dev
**/logs              @example-dev
/.github/CODEOWNERS   @example-owner
三个必须知道的规则
  • 最后一条匹配的模式生效（和 .gitignore 一样），所以 * 要放最前面。
  • 同一模式的多个负责人必须写在同一行，写成两行的话第二行会覆盖第一行。
  • PR 使用目标分支（base branch）的 CODEOWNERS，不一定是默认分支。新分支上的分工表未进入目标分支前，不会直接决定当前 PR 的负责人。

保护分工表时，还要把它纳入负责人规则、启用必需负责人评审，并检查旁路权限。只加一行名字不能防止所有未授权修改。

机制 4GitHub Actions：让机器先过一遍

GitHub Actions 按 YAML 中配置的事件与过滤条件运行，不是放进去就会响应所有 push 和 PR。Runner 可以是 GitHub 托管环境，也可以自托管；后者不保证每次都是干净的虚拟机。

它把「测试跑没跑过」从作者的口头保证，变成页面上一个红绿勾——这是 review 之前最省事的自动化。

下面是 Node.js 项目的教学示例，不是本静态官网的现有配置。使用前要有一致的 package.json、锁文件及 test 脚本，并选择项目支持的 Node 版本。Node 20 已结束支持，此例使用 24；参见版本状态。npm ci 会检查依赖与锁文件是否一致。

name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - name: 检出代码
        uses: actions/checkout@v4

      - name: 设置 Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '24'

      - name: 安装依赖
        run: npm ci

      - name: 运行测试
        run: npm test

本官网是静态页面，不要照抄不存在的 npm 测试。可按需检查 HTML、链接、敏感内容，并验证桌面和手机上的实际交互。静态检查也可能漏错；没有依赖不等于不需要行为验证。

AI 时代最需要警惕的一件事：CI 作弊

GitHub 的 agent PR 文章提醒：为了让 CI 变绿而删除有效测试、跳过检查或添加 || true，应被重点质疑。这是评审建议，不是平台自动识别并阻止所有此类改动的承诺。见原文。

所以 review 时一定要先看有没有动 CI 配置和测试文件——这是 AI 写代码时代新增的一条红线，对人写的 PR 同样适用。

2026 年的 GitHub 上已经有一整套 AI 功能，它们在团队流程里承担的角色各不相同：

角色它在哪一步你要做什么
补全 / 编辑本地 IDE 里照常写，改动还是你负责
规划（Plan Mode）写码之前回答它的澄清问题，确认计划

不要把某个 agent 的分支或审批限制套到所有 AI 产品上，平台规则也会调整。工作室的原则是：AI 产出的 PR 仍按仓库的权限、必需检查和人工评审流程处理，不能因为是 agent 开的就直接合并。

GitHub 自己对自动 review 的免责声明，原文大意

GitHub 提醒，Copilot 可能漏报、误报，建议也未必正确。需要验证反馈并结合人工审阅。这是文档意思的概述，不是逐字引语。见官方说明。

换句话说：自动 review 是帮你筛出可疑点，不是替你把关。把机器的判断当作「值得看一眼的地方」，而不是「已经检查过了」。

团队具体怎么协作：从零到合并

下面以 main 为目标分支演示，实际工作以负责人指定的仓库、工作树和分支为准，不要直接套到正式发布分支。命令中的文件名和分支名是示例，使用前先替换。

第一步：每天开工，先同步

从较新的目标分支开始，通常能减少后续整合成本；旧代码不一定导致无关 diff，但可能增加冲突。先看状态，妥善保存现有改动；同步被拒绝时先确认原因，不要强行覆盖。

git status                      # 先确认没有未处理的改动
git switch main
git pull --ff-only origin main   # 分叉时会拒绝，不自动制造合并
git switch -c feat/12-login-page

第二步：写代码，分次提交

git status                  # 永远先看这个
git diff                    # 看具体改了什么

git add 具体文件路径          # 推荐：明确指定要提交什么
git commit -m "feat(auth): 添加登录表单组件"

commit message 建议用固定前缀，一眼能看出改动性质：

前缀含义
feat新功能
fix修 bug
docs文档
refactor重构，不改功能
chore杂务（依赖更新、配置）

第三步：推到 GitHub，开 PR

git push -u origin feat/12-login-page

然后在 GitHub 开 PR，写清做了什么、实际怎么验证、关联什么任务。下面仍是虚构的 Node.js 登录练习，不是我们项目的真实接口或启动方式：

不合格的描述

修了一些东西

合格的描述

做了什么：新增练习项目的登录表单。
怎么验证：运行项目已有的开发脚本，用测试账号验证成功、失败与错误提示。未验证的场景另列。
关联：Closes #12（仅在确有这个 issue 且适用时填写）

还没写完就先开成 draft PR，等人看个方向；写完点 Ready for review，这时才会正式触发 review 流程。

第四步：PR 打开后，main 又更新了怎么办

这是新手最容易忽略的一步。如果不管，PR 会越拖越难合。

如果 PR 页面提供 Update branch 且没有阻碍，可按团队约定更新。按钮不一定存在；有冲突、无权限或配置不匹配时，要先确认原因。

命令行（更可控）：

git status                    # 先确认工作目录干净
git fetch origin
git switch feat/12-login-page
git merge origin/main         # 在功能分支整合，不重写旧提交
# 如有冲突：修改冲突文件，git add 明确路径，再 git merge --continue
git push
强推不是日常同步步骤

上面的 merge 流程通常不需要强推。确需重写自己独占且获准改写的分支时，--force-with-lease 比 --force 多一层检查，仍不是安全保证：默认检查依赖本地远程跟踪引用，后台 fetch 等操作可能改变它。先确认远端提交及协作者状态，不向受保护主干强推。见Git 说明。

第五步：处理 review 意见

拿到意见之后，在同一个分支上继续改，不要为 review 意见新开 PR——这样 reviewer 能在同一个页面看到完整的对话历史。

回复评论时，说清楚「改了什么、为什么这么改、验证了没有」，而不是只回「好的，我改一下」——后者等于让人家自己再去看一遍 diff。

落实修改，回复依据，并与评审者确认后按团队约定标记 Resolve conversation。关掉线程不等于问题已经解决，也不等于批准；启用了必需对话解决规则时，未解决线程会影响合并。

第六步：合并，然后立刻同步

合并后，为下一项任务准备新的起点

确认 PR 已进入目标分支，再更新本地。旧分支不要直接接着做下一项任务；清理前确认提交确实保留，并妥善保存未提交改动。

git status
git switch main
git pull --ff-only origin main
git fetch origin --prune       # 清理失效的远程跟踪引用
git branch -d feat/12-login-page

Squash / rebase 合并后，git branch -d 可能因提交祖先关系不同而拒绝。先核对 PR 和分支内容，不要顺手改成 -D。若不确定，就保留分支请负责人确认。见分支删除说明。

Review 时具体看什么

可以按下面顺序检查。它是入门清单，不代表覆盖全部问题；重要改动需要更深入的验证。

  1. 先看 CI。任何一个红叉都先别细读，先问为什么。

  2. 看改动范围。优先让一个 PR 围绕一个明确目标。文件多、行数多时评估是否需要拆分；一致的批量修改不一定要按固定数量切开，关键是能理解、验证和回退。

  3. 重点看敏感文件的变化：CI、测试、依赖与锁文件、生成文件。它们并非一律不能改；要有任务依据，且不能靠削弱有效检查掩盖失败。

  4. 安全检查。留意密钥、用户数据、认证和权限变化，以及输入如何进入 SQL、命令或路径。搜索 password、token 等只是辅助，搜不到不证明没有泄漏或漏洞。

  5. 真的跑一遍。reviewer 有责任真的把它跑起来，而不是只看 diff。跑不起来就说跑不起来，这本身就是重要信息。

  6. 兼容性。核对接口、数据库、函数签名和依赖变化。部分问题需要集成环境或真实设备验证；把尚未验证的边界写清楚。

两个人同时改会怎样

Git 通常能自动整合不重叠的文本改动，但冲突不只来自同一行：重命名、删除与修改等也可能冲突。自动合并成功也不保证功能正确，跨文件改动可能产生逻辑冲突。

情况结果
改不同文件通常可自动合并，仍可能有接口或逻辑冲突
同一文件、不同区域通常可自动合并，仍需测试
同一位置作不同修改可能产生文本冲突，需要人工决定
一方删除，另一方修改；或重命名冲突也可能冲突，不一定出现普通文本标记
未受保护分支上，远端已有本地未包含的提交普通 push 通常被拒绝；先查差异，不要强推覆盖

遇到 push 拒绝时，先只读检查差异。如果是受保护主干要求 PR，就改走团队流程，不把直接推 main 当作日常协作方式：

git fetch origin
git log --oneline --left-right HEAD...origin/main
# 先确认当前分支与远端名称，再与负责人决定整合方式。

冲突怎么解决

下面是 git rebase origin/main 时的示意：HEAD 一侧是基于目标分支已经整合的内容，另一侧是当前正在重放的功能提交。不能一概解释为「我的 / 远端的」；merge 的语境又不同，要结合命令和 git status 判断。

<<<<<<< HEAD
（目标分支，以及此前已成功重放的内容）
=======
（当前正在重放的功能提交内容）
>>>>>>> <正在重放的提交>

处理步骤：

  1. git status —— 看 Unmerged paths 那一段，那里列的就是冲突文件

  2. 打开冲突文件，把三个标记行全部删掉，只留下你要的内容（可能两边都要，手工组合）

  3. git add <冲突文件路径> —— 逐个暂存已确认的解决结果，避免顺带提交无关改动

  4. rebase 用 git rebase --continue；merge 用 git merge --continue。先核对状态，不混用命令

  5. 重新跑一遍测试，再 push

确认当前操作后，可用对应的 git rebase --abort 或 git merge --abort 放弃。操作前已有的未提交改动不一定都能重建，所以开始整合前先妥善保存，不要把 abort 当备份。

最后一步千万别省。冲突标记漏删一个，代码会语法报错；更常见的是语法没错但逻辑错了——两边的 CSS 合并后样式打架，两边的判断条件合并后互相覆盖。

怎么从源头减少冲突

  • 一个 PR 围绕一个明确目标。范围越容易理解，越有利于协作；不能凭改动行数推算固定的冲突概率。
  • 重构单独开 PR，不要和功能改动混在一起。
  • 依赖清单和锁文件一起维护。依赖升级可以单独成 PR，但相关代码调整应一起验证；不要为了拆分而制造不一致的中间状态。
  • 统一格式化工具与配置。大范围格式化尽量与逻辑修改分开并提前协调，但仍可能与其他改动冲突。

合并方式怎么选

方式结果什么时候用
Merge commit保留全部提交，加一个合并点需要保留完整历史时
Squash 合并把 PR 改动压成一个提交希望主干按完整任务记录；不是所有团队都适用
Rebase 合并逐个提交放到主线，线性你们能保证每个提交都是有意义的原子提交

推荐 Squash 合并：历史干净、主干上的提交信息完全可控、PR 里的细碎提交（「改个错别字」「处理 review 意见」）不会污染主干。

用 squash 有一个配套规则必须知道

建议 squash 合并后，从更新后的目标分支新开分支。复用旧分支可能带来重复提交记录或后续整合困扰，但不是每次都必然产生相同冲突。以目标分支的实际历史和团队约定为准。

常见事故与处理

一、force push 覆盖了同事的提交

先停止向受影响分支推送，并通知协作者。检查同事的本地分支、reflog 或其他保留引用。reflog 是本地记录，有保留期限，不保证包含全部历史或未提交文件。找到并核实旧提交后，可先建恢复分支；不要直接覆盖共享分支。以下 SHA 是占位例子：

git switch -c 分支名-recovered a1b2c3d
git push -u origin 分支名-recovered

预防：共享主干禁止强推，核对分支保护的旁路权限。需要重写独占分支时先协调；--force-with-lease 只是补充检查，不是恢复保证。

二、密钥泄露

立即通知负责人，并尽快撤销或轮换已暴露的凭据。优先使泄漏的旧凭据失效，不要机械地等所有环境迁移完成才处理；具体顺序兼顾暴露风险与服务影响。见GitHub 应急指南。

  1. 确认泄漏范围，尽快在服务商处撤销或轮换旧凭据
  2. 通过安全渠道更新服务器、CI 和本地配置，验证服务
  3. 检查异常使用记录、用户影响与残留副本，并记录处理过程
  4. 与负责人评估是否需要清理 Git 历史；如需使用 git filter-repo，先授权、备份并协调协作者，不能直接改写共享历史

只删文件是不够的——密钥会传播到 fork、备份和 CI 日志里，删掉文件不等于密钥消失，必须撤销。

预防：密钥放在受控的服务端配置、环境变量或凭据管理工具里。仓库里的 .env.example 只留假值；.gitignore 不处理已提交历史，前端打包的变量也可能公开。推送保护能拦截部分已识别的密钥，但不能识别所有秘密或替代人工检查。

三、误删分支

如果对应的已关闭 PR 提供 Restore branch 按钮且你有权限，可按提示恢复；按钮不保证始终可用。若已找到并核实提交，也可用 git branch <分支名> <sha> 重建。先确认提交仍可获取。

没开过 PR 的分支恢复就没有保证了。预防：分支保护里把「Allow deletions」保持关闭。

四、想撤销一个已经合并的提交

协作主干通常用新的 revert 提交撤销改动，而不是 reset 后强推。git revert <提交> 适用于普通提交；撤销 merge commit 还需正确选择主线父提交，不要盲目加 -m 1。请负责人确认，并通过 PR 验证回退效果。GitHub 的 Revert 按钮也可能因权限或冲突不可用。见Git 说明。

如果只记住五句话

  1. 下一个任务从更新后的目标分支开始。先处理未提交改动，再用 git pull --ff-only 同步；分支删除被拒绝时先核对，不要直接强删。

  2. 不擅自重写共享历史。rebase 与强推需确认分支确实独占、操作获准；lease 不是免责按钮。

  3. 一个 PR 只做一件事。这是降低冲突和 review 成本的最大杠杆。

  4. 项目第一天就配好分支保护和 CI。它不是「以后有空再说」的事，是让错误难以发生的前提。

  5. main 永远只走 PR。包括你自己。

07 / DECISION第七章 · Jev：让 AI 做有边界的判断

目标：认识分类、评分和概率判断这类任务，理解 Jev 与聊天模型的分工。先用虚构案例做练习，不把一个模型的输出直接接到真实业务操作上。

一、它不是另一个聊天框

「帮我写一份公告」需要组织语言；「这条反馈属于使用问题、疑似 Bug，还是功能建议」需要在明确的选项中判断。Jev 主要面向后一类任务。

Jev 是 TypeSafe AI 提供的模型，官方将它归为 System One 模型：给出背景信息和规定好的问题，返回相应的结构化判断，而不是自由撰写文章。「决策模型」在这里描述产品用途，不是所有 AI 通用的分类标准。见官方介绍。

先了解，不必为了这一章另买一个工具

本章按官方 Playground 和托管 API 的入口介绍，不提供本地权重部署教程。SDK 或第三方类似项目开源，不代表 Jev 的模型权重也开源。官方体验与接入方式见快速开始；产品信息核实于 2026 年 10 月 2 日。

二、三种问题：选哪类、处在哪档、是否成立

先把问题定义好，再让模型判断。下面是官方的三种问题类型；校园场景只是帮助理解的例子，并不表示我们已经在小程序中接入了 Jev。

类型适合问什么怎样读结果
Choice · 分类反馈更接近「使用咨询」「疑似异常」「功能建议」还是「信息不足」？这些类别没有高低顺序。返回所选类别、各类别的概率及 confidence。类别说明要清楚，尽量避免互相重叠。
Score · 有序评分材料完整程度更接近「缺关键信息」「基本可判断」「信息较完整」哪一档？档位有顺序。返回量表上的分数、概率分布及 confidence；分数可能位于两档之间，不一定是整数。
Noul · 是非概率这段反馈是否明确提到了「登录已过期」？一次只问一件事。返回命题为真的概率，范围为 0 到 1；没有独立的 confidence 字段。接近 0 是倾向「否」，不是低置信度的意思。

同一次请求里的问题分别作答，不能假定第二题会读取第一题的答案。如果下一步依赖前一步，应由程序显式串起来。类型与结果结构见官方问题类型说明。

注意问题的边界：「用户有没有提到登录过期」可以看文字；「这个账号的登录状态是否真的过期」必须核对系统实际状态。模型不能凭一段描述替代后台检查。

三、不要把所有工作都交给它

确定的规则 → 普通程序必填项有没有填写、成员有没有发布权限、版本号是否合法，这些应按明确规则检查，不需要靠模型猜。
有限的判断 → 比较合适的方案对描述做初步分类、按量表评价，可以比较规则、普通分类器、聊天模型和 Jev。任务简单时，规则就可能够用。
解释与写作 → 生成式工具把确认过的更新日志写成公告、整理文案，需要生成语言。Jev 的分类结果不等于一篇可以发布的公告。
执行与责任 → 权限和人模型判断不等于授权。发布公告、改账号、合并代码、决定版本，仍由对应流程和负责人控制。

聊天模型也可以按 JSON 格式输出分类结果。区别不能简化成「聊天模型不会分类」或「只要结构化就正确」：格式合规与判断正确是两件事，两条路线都需要用真实任务的样本验证。

TypeSafe 将训练路线称为 RLCD，即「面向校准决策的强化学习」，强调概率判断的校准。这是官方对自身方法的定位，不是我们已经独立复现的效果。宣传中的速度、成本和准确性，不能直接当作校园业务的实测结果。见项目官网。

四、看一个校园反馈的练习

假设有一条虚构反馈：「教材查询提示登录过期，不知道下一步怎么操作。」我们只想做初步分类，不要求它判断后台原因，也不让它替用户操作账号。

下面展示官方请求格式中的一种写法，仅供理解。它不是可以直接粘到静态网页里的完整调用代码，也没有使用真实用户资料。

{
  "model": "jev-latest",
  "state": "用户反馈：教材查询提示登录过期，不知道下一步怎么操作。",
  "questions": {
    "feedback_kind": {
      "type": "choice",
      "instructions": "按当前描述做初步分类，不推测未提供的后台原因。",
      "criteria": {
        "usage_question": "询问已有功能的使用方法",
        "possible_bug": "描述预期与实际行为不一致，疑似功能异常",
        "feature_request": "提出新的功能或体验建议",
        "insufficient_info": "现有信息无法支持前三项判断"
      }
    }
  }
}

这里的 state 是待判断的材料，instructions 是判断要求，criteria 是每个选项的含义。不要只写几个缩写，就期待模型懂得我们的部门约定。

jev-latest 是会随发布变化的别名。测试或交接时，要记录响应中的实际模型版本；需要固定版本时，按官方当前可用的标识配置。见模型说明。

获准使用并去标识化的反馈 + 明确分类标准
                  ↓
           模型给出参考分类
                  ↓
     程序检查结果格式，模糊情况交给人
                  ↓
     客服核对信息 → 运营整理 → 技术评估与实现

这只是练习方案，不是现有小程序的运行机制。我们的部门边界不变：客服收集和核对反馈，运营归纳合理的需求与 Bug，再提交技术部。模型不能绕过运营直接安排开发，也不能自动承诺修复时间。

五、概率不是保证，confidence 也不是正确率

Choice 和 Score 的 confidence 是根据结果的概率分布计算出来的量，算法随问题类型不同；不能一概把它当成「最高类别概率」，更不能读成「这一次必然有这么高的正确率」。Noul 则直接给出是非概率。见官方置信度说明。

「校准」可以粗略理解为：在足够多的类似预测里，模型给出的概率与实际结果频率是否相称。它是需要用一批案例检验的性质，不是对单个判断的担保。

没有通用的「超过 0.9 就自动执行」

分类错一条咨询与错误操作账号，代价完全不同。阈值应根据任务、样本和出错成本来定；信息不足时允许不作结论。即使模型很肯定，也不能越过权限、人工审核或产品事实。

官方当前模型说明强调文本输入及英语表现；不要默认它已经适配我们的中文表达、校园简称和隐含语境。中文样本要单独测，图片、语音、视频也不能直接按文本接口提交。见输入与语言支持说明。

六、新成员怎么开始

  1. 只选一个小问题。例如「反馈初步分类」，先写出每类的定义，以及模糊案例应怎样处理，不要一开始就做自动客服。

  2. 准备可用的样本。先用虚构例子；真实材料必须获准并去标识化。由人按统一标准标注，保留容易混淆和信息缺失的案例。

  3. 比较而不是追热点。用相同案例比较规则、已有工具和 Jev，记录错分、漏掉重要异常、需要人工复核的数量，以及实测耗时与成本。

  4. 先旁路观察。只产生建议，不影响用户；核对结果后再讨论是否接入。交接时留下样本范围、分类标准、实际版本、已知错误和负责人。

API 密钥与用户信息都不是练习素材

密钥不能写在公开仓库或静态网页里，应由受控服务端保存。校园账号密码、验证码、访问令牌，以及未经允许的用户记录，不能发给外部模型。先确认团队批准的数据范围与调用预算。

这一章最重要的不是学会某个接口，而是把问题问清楚，把结果接在有边界的流程里。模型可以帮助判断，人仍要负责标准、验证和后果。

08 / COMFYUI·FILM第八章 · ComfyUI：从一张图到一段 AI 短剧

目标：认识节点工作流，知道 AI 短剧从剧本到交付有哪些环节。先做一个短镜头，再尝试组织完整故事；本章不是安装全套模型或训练角色的要求。

一、ComfyUI 是工作台，不是模型本身

ComfyUI 是开源的节点式生成工具，可以组织图像、视频、音频等工作流。你在画布上连接步骤，让数据从输入流向输出；具体能生成什么，还取决于接入的模型与节点。

本地运行的开源核心可以免费使用，但电脑算力、电力和存储仍有成本；Comfy Cloud、部分调用外部服务的 Partner Nodes 可能收费。不要把「软件开源」理解为「所有工作流都免费」。见官方产品说明。

节点 Node
一个处理步骤，如加载模型、读取图片、设置文字条件、执行采样、保存结果。一个节点不是一位会自己规划的 agent。
连线 Link
把上一步的输出交给下一步。接口有数据类型，不是看起来能接就能接。
工作流 Workflow
节点、连线与参数组成的流程，通常可保存为 JSON。它描述怎样运行，不会把所有模型文件一起装进去。
模型 Model
实际参与生成的权重文件。同一套软件可以换模型；不同模型需要相应加载器、条件和资源。

浏览器只是操作界面，计算可能在本机，也可能在远程服务器。先弄清连接的是哪台机器、素材会发往哪里、费用由谁承担。工作流概念见官方说明。

二、先跑通一张图，再谈视频

  1. 确认已有环境。先找负责人确认可用的电脑、运行方式和模型，不要为了入门一次下载所有热门模型。可从官方首次生成教程认识基本步骤。

  2. 从官方模板开始。在 Templates 入口或 Workflow 菜单的模板浏览器里选一个基础图像工作流。先看每个节点的作用，不急着加复杂扩展。

  3. 核对依赖。模板可能提示缺模型。确认来源、许可、适用加载器及目录，再由获准的成员补齐；导入 JSON 不等于安装完环境。

  4. 一次改一个条件。先保存一次成功输出，再修改提示词或一个参数，比较实际图片。失败时记录报错，不靠随机改十个参数碰运气。

  5. 保存可交接的记录。保留工作流、输入素材、参数与使用版本。只发一张生成图片，别人通常无法知道它是怎么做出来的。

模板入口和模型提示可能随版本变化，按官方模板说明核对。以下是基础图像工作流的概念图，不是所有模型通用的完整接线图：

加载模型 + 文字条件 + 初始潜在表示
                    ↓
                  采样
                    ↓
          解码为可见图像（常见步骤：VAE）
                    ↓
                预览与保存

「潜在表示」暂时理解为模型内部处理图像的一种表示就够了。新手先认识输入、主要处理步骤和输出位置，没必要第一天就弄懂数学细节。

三、AI 短剧不是按一下按钮就交片

下面是一条建议的制作路线，不是 ComfyUI 自带的一键完整短剧功能。ComfyUI 可以承担其中的生成环节；写作、声音制作、剪辑和审核往往还要配合其他工具。

剧本 → 分镜 → 角色与风格参考 → 关键画面
                                      ↓
                                  逐镜头视频
                                      ↓
                  配音 / 音效 / 必要的口型处理
                                      ↓
                       剪辑、字幕、检查与交付
环节要留下什么先检查什么
剧本人物目标、冲突、转折、对白或旁白。观众能否理解事情为什么发生？有没有只靠画面无法表达的信息？
分镜镜头编号、景别、动作、目标时长、声音说明。一个镜头不要塞太多动作；镜头之间能否接起来？
美术与关键画面角色参考、服装与道具约定、场景风格、各镜头画面。角色是否一致？构图是否给动作和字幕留出空间？素材是否获准使用？
视频生成分镜对应的短片段，保留通过检查的版本。人物、手、物体关系、运动与闪烁。不能只看第一帧漂亮。
声音与剪辑配音、音效、剪辑工程、字幕和成片。台词、节奏、音量、字幕错字、画幅与导出质量。

第一支片子建议少人物、少场景、少复杂动作。旁白配简单画面通常更容易控制；这只是练习建议，不保证任何模型都能一次生成成功。

四、视频模型怎样接进来

文生视频 · T2V主要用文字描述生成视频，适合探索画面和动作。角色长相与构图的控制需要另外评估。
图生视频 · I2V从参考图出发生成运动。先做好关键画面，可以减少起始画面的不确定性，但后续仍可能变形或走样。
首尾帧与其他条件部分模型接受起止画面、姿态或其他条件。支持哪些输入取决于具体模型与工作流，不是所有视频模型都有。
音视频联合生成部分模型可以一起生成画面与声音。不能据此保证指定的中文台词、声音身份或口型准确，仍要听看检查。

可以看官方的Wan 2.2 视频教程和LTX-2 音视频教程认识不同路线。它们是示例，不是本章对「最新最强」的排名；模型许可和运行要求分别核对。

能否在自己的电脑上跑，要看模型变体、分辨率、帧数、显存、卸载策略和节点实现。不要把某个低负载示例的要求套到全部工作流，也不要仅凭「别人能跑」就购买显卡。

练习时先选环境确实支持的小任务，少量尝试并记录耗时与失败。降低尺寸或帧数也要符合模型要求；云端运行则先设预算，不要连续重试到忘了费用。

五、角色一致性：先约定，再生成，再检查

为角色准备一张经过确认的参考图，再写清发型、服装、配色、道具和整体画风。不同镜头沿用同一套约定，发现漂移及时修正，不要等剪辑时才发现主角每次都换了脸。

常见办法可以帮助什么不能保证什么
参考图 / 图像编辑在支持的模型与节点中约束外观或起始画面。运动过程中始终保留同一张脸、同一件衣服。
LoRA兼容时，帮助表达特定角色或风格。随便一份 LoRA 都能跨模型使用；也不代表素材与训练数据许可合格。
ControlNet 等结构条件在支持的方案中提供姿态、边缘、深度等引导。结构引导本身不等于人物身份锁定。
局部重绘修改指定区域，修补画面问题。区域外完全不变，或修好的静帧能自动保证整段视频一致。

这些能力需要模型、节点及输入相互兼容，基础概念见官方模型说明。入门不要求训练 LoRA；先用获准的参考素材完成一个镜头就有意义。

固定 seed 不是「锁脸按钮」

seed 是随机过程的种子。提示词、模型、工作流或环境改变后，相同 seed 不能保证同一角色或完全一致的输出。判断一致性要看实际画面，不能只看参数相同。

对白需要准确时，可以先单独确认台词和配音，再按支持的方案做口型或采用旁白。不要默认每个视频工作流都会生成音轨，也不要把自动生成的含糊声音当作已经完成配音。

六、一个新人能开始的短片练习

练习题：一位虚构同学带错了书。以一个角色、一个场景、三到五个镜头，尝试做一支约 20—30 秒的小片。时长只是成片目标，由多个片段剪辑实现，不是承诺模型一次能输出这么长。

  1. 写清故事。先用几句话说明发现带错书、想办法应对、最后怎样收尾。写好旁白，避免依赖复杂多人对话。

  2. 先做分镜与参考。确定画幅、角色和场景，给每个镜头写一个主要动作。先确认静态关键画面，再生成视频。

  3. 只完成第一个镜头。检查整段运动、手与书的关系、人物外观。合格后再复制制作方法到其他镜头，失败就缩小动作范围。

  4. 剪成故事。加入确认过的配音与字幕，调整停顿和切换。生成片段只是素材，不必原封不动地全用上。

  5. 交给另一位成员复核。检查是否看得懂、是否有明显变形、台词与字幕是否一致，并留下可继续修改的文件。

镜头：S01
用途：让观众发现「带错书」
画面：固定中景；角色低头看手里的书
约束：沿用角色参考；服装、书本外观保持一致
声音：旁白「上课前五分钟，我才发现……」
时长：先定剪辑目标，再按模型支持的长度生成
检查：脸和手不明显变形；书本关系合理；无明显闪烁

这里的分镜描述是计划，不是某个模型的专用提示词。实际工作流支持什么输入，要看模板和文档；可以用 AI 帮忙改写，但不能用它的保证代替看片。

七、把流程交给下一位成员

  • 创作材料：剧本、分镜、角色与场景参考、提示词、素材来源与使用许可。
  • 运行材料：工作流 JSON、输入文件、模型与自定义节点的版本、关键参数、seed，以及运行环境说明。
  • 交付材料：分镜对应的视频与音频、剪辑工程、字幕、成片，以及检查意见和待修改项。
  • 过程记录：成功与失败的条件、实测时间、云端费用、人工修改过哪些地方、下一位成员应该先检查什么。

部分输出格式或节点会把工作流写入文件元数据，但转码、压缩或平台传输可能移除它。单独保存 JSON，不要只依赖图片里的信息。JSON 本身也不包含全部权重与输入素材，不等于能像素级复现。见工作流保存说明。

对外分享前，检查工作流与元数据里有没有私人路径、敏感提示词或服务凭据。可复现材料先按团队约定保存，不要为了公开教程把内部素材一起发出去。

八、常见卡点与发布边界

现象优先检查
导入后节点缺失或标红工作流所需的核心版本、自定义节点及依赖。不要看见报错就安装来源不明的整合包。
找不到模型或加载失败权重是否齐全、目录与加载器是否匹配、格式是否兼容。改文件名不会把一种模型变成另一种。
显存不足或生成很慢具体报错、模型变体、尺寸、帧数与内存策略。一次失败不能直接证明显卡损坏或必须升级。
角色漂移、动作变形、画面闪烁参考是否一致、动作是否过于复杂、模型是否支持所需控制。尝试缩短镜头、简化动作或重设计分镜。
没有声音或对白不准模型与工作流是否支持音频，是否有输出音轨。必要时分开做配音与剪辑，不假定只是某个开关没勾。
自定义节点不只是「一块积木」

安装自定义节点会运行代码并引入依赖。先核对来源与维护情况，在可恢复的环境里测试；外部服务节点还要确认数据去向、密钥与计费。不要为跑一个工作流随意关闭系统安全措施。见官方自定义节点说明。

正式发布前，分别核对模型、角色参考、音乐、字体和其他素材的使用许可；涉及真人肖像或声音，要先确认授权，不做未经允许的声音克隆或冒充。发布平台的 AI 内容标识与其他要求也要逐项核对，不能用「AI 生成的」作为免责理由。

本章产品与教程信息核实于 2026 年 10 月 2 日。先做好一个镜头，再组织一个故事，最后把可继续修改的流程交出去。这比收集一堆还没跑通的工作流更适合作为入门目标。

写在最后HOW TO VIBE WELL

怎么成为一个
好的 vibe coder。

Vibe coding 这个词来自 Karpathy 在 2025 年 2 月的帖子。下面概述其语境，不把节选译文冒充完整原话。

他的描述大意是：让 AI 持续生成代码，自己不再仔细检查，最后代码超出自己的理解；他把这种体验放在可以丢弃的周末项目语境里。可参考 Simon Willison 对原帖的引用与讨论。

这不等于作者对所有 AI 编程下了「不适合正式项目」的统一结论。需要区分：盲目接受、不理解代码，与借助 AI 但仍审查、测试并负责。

所以真正的问题不是「要不要 vibe coding」，而是：怎么用它的速度，同时不落到「代码没人能维护」的地步。

Simon Willison 的讨论强调了类似区分。借此，本文给新成员的建议是：

提交前弄清改动的用途、影响范围与验证结果；解释不了的部分，先查清或请负责人一起审。

这不是说新手必须看懂每一行——那不现实。而是说你得知道它在做什么、能回退、出了错能修。达不到这个标准之前，把代码当成草稿，别当成产品。

风险是真实存在的，不只是理论担忧

第三章列出的研究说明，在那些特定样本与设置下，功能通过并不能保证安全通过。不能把论文中的比例直接套到我们的小程序；真正需要的是针对项目风险做验证。

结论不是「别用 AI 写代码」，而是：功能跑通不等于可以上线。

下面六条总结基础六章的协作习惯。后两章的决策与媒体制作，也需要明确边界、验证结果并保存过程；熟悉之后，再把这些习惯用到自己的任务里。

01

用 AI 提速度，不用它替你负责

它可以写得很快，但出了事是你在承担。「先跑起来」阶段可以不看每一行；「要给用户用」阶段必须能解释、能验证。

02

先看计划，再让它动手

一句「先别写，给个方案」能省掉大量返工。看不懂的计划不该被执行。

03

每个任务前后都留检查点

用 Git 记录可恢复的代码状态；未提交文件和外部数据另外保护。检查点降低试错成本，不保证所有操作都能撤销。

04

规则写进项目说明，别靠记忆

使用工具支持的 AGENTS.md 等文件，保持精简、准确，并确认已加载。它是协作说明，不是安全隔离机制。

05

看验证证据，而不是完成声明

要求实际运行、检查 diff，并记录通过与未验证的部分。功能正确与安全是不同的检查目标。

06

代码最终要交给人

GitHub 仓库是这个工作里最重要的资产。它让任何人（包括三个月后的你）能看懂、改得动、接得下去。
