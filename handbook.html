01 / 关于AI第一章 · 关于 AI

目标：把 LLM、Harness、Agent 这三个在 2026 年反复出现的概念讲清楚，并列出本方向最常用的一些编程语言。

LLM（Large Language Model，大语言模型）：基于 Transformer 架构、在海量文本上预训练的概率模型。给定一段上下文，预测下一个 token，并以此生成连贯的自然语言或代码。它不检索事实，生成的是「最像合理继续」的文本，所以在事实性、数学性、确定性任务上可能出错，需要外部工具或人来兜底。2026 年的主流 LLM 已经普遍具备：长上下文（数十万到百万 token 量级）、工具调用（function calling / tool use）、多模态输入（文本 + 图像 + 音频 + 视频）、结构化输出（JSON / 代码）。这些能力本身不等于「Agent」，它们是 Agent 用来决策的「大脑」。

Harness：包裹在 LLM 外面的运行时基础设施。2026 年流行的总结是 Agent = Model + Harness。LLM 本身是无状态的，不会主动调工具，也不保证自己写出的代码能跑；Harness 负责把这些事补上（管理会话、调度工具、维护上下文、持久化状态、隔离沙箱、设置权限与护栏）。判断一个系统是不是 Harness 的四个必要条件（arXiv 2606.10106）：① Agent Loop（推理 → 行动 → 观察 → 再推理的循环）；② Tool Interface（让模型能感知并修改外部环境）；③ Context Management（主动管理流入流出的信息）；④ Control Mechanisms（不依赖模型「愿不愿意服从」的限制、验证器、确定性处理）。LangGraph / CrewAI / AutoGen 这类「框架」是用来构建 Harness 的工厂，不是 Harness；Claude Agent SDK / OpenAI Agents SDK 是零件，不是 Harness。真正的 Harness 实例：Claude Code、Codex CLI、Aider、Cline、OpenHands、SWE-agent、Hermes Agent 等。

Agent：「LLM + Harness」组合之后跑起来的系统形态。给定一个目标，自己决定下一步做什么、调用哪些工具、怎么验证结果，直到目标完成或触发停止条件。Agent 与「聊天机器人」、「RAG 检索增强」的根本差异是自治度：聊天机器人只回答一次；RAG 检索完就生成回答；Agent 检索、决策、执行、观察、再决策。2026 年主流 Agent 架构的四个角色：Planner（拆目标为子目标）、Executor（在当前状态下决定调用哪个工具的 LLM 调用，token 消耗大头）、Memory（短期 = 上下文窗口里的对话缓冲，长期 = 向量库/结构化数据库/文件）、Tools（网页搜索、代码解释器、数据库查询、文件操作、API、其他 Agent）。Anthropic 2024 年 12 月的《Building Effective Agents》还区分了 Agentic Workflow（开发者写好图，LLM 在节点里填内容）和 AI Agent（LLM 在运行时自己决定图的下一条边）。

常用语言（按本项目使用频率排序）：JavaScript / TypeScript（小程序前端与构建工具链的事实标准）、Python（AI 工具链的事实标准：训练、推理、评测、agent 编排）、PHP（本项目后端云函数与 API）、SQL（从 PostgreSQL / MySQL 取数）、Shell（bash / PowerShell，构建、部署、调试绕不开）、Rust（新一代 AI 基础设施语言，Hermes Agent 本身、llama.cpp、tokenizers、Polars 等）、C / C++（底层推理引擎实现语言）、Mojo（Modular 出品、Python 语法的超集、能编译到原生机器码，2026 年仍是早期阶段）、Julia（科学计算与数值分析方向的语言）。入门优先级：JavaScript / TypeScript 与 Python 先扎实；SQL 与 Shell 同步学；PHP 看后端代码时跟着读；Rust / C++ 在真正碰到性能瓶颈或读底层代码时再深入；Mojo / Julia 了解即可。

这一章最重要的一句话

模型只会「说」，Harness 让它能「做」。读下一章之前记住这句：Agent = Model + Harness。下面讲的就是 Harness 到底长什么样、怎么用。

02 / ChatGPT第二章 · 购买 ChatGPT

目标：完成 ChatGPT 账号注册、选择适合自己的订阅档位（Free / Plus / Team / Pro）、完成首次支付，并把 ChatGPT 用到至少一个真实任务里。

为什么专门讲 ChatGPT 的购买方式。一方面是因为这个不是国内的；另一方面是它便宜而且好用。

三种购买方案

前提：三种方案都要求自备稳定的网络环境（俗称「梯子」），并且需要海外 IP 才能完成支付与订阅。请先把网络环境确认好再开始操作。

03 / HARNESS第三章 · Harness：让 AI 真正动手

目标：搞清楚 Harness 是什么、为什么不能只用网页版聊天，以及怎么在电脑上装一个能真正读写文件、跑命令的 AI 编程助手。

一句话理解 Harness

上一章说过，LLM 是「大脑」，Harness 是「身体」。大脑能想，但手不能动、眼睛不能看、耳朵不能听。Harness 就是把这副身体接上去的那层运行时。

你在 ChatGPT 网页框里聊天的时候，那基本只有一个大脑。而 Claude Code、Codex 这类工具才是完整的身体：它能读你硬盘上的文件、能改代码、能在终端里跑命令、能把报错信息再读一遍。

这就是本章存在的理由：想让 AI 帮你做实事，就得用 Harness，只用网页版聊天是做不到的。

Harness 到底在干什么

四件事，对应上一章说的四个必要条件：

循环想 → 做 → 看结果 → 再想。模型每做一步都会拿到真实反馈，而不是一口气把代码全写完就交差。
工具把「读文件」「改文件」「跑命令」「上网」包装成模型能调用的东西。没有工具，模型只能输出文字。
上下文决定每一轮把哪些内容喂给模型：项目结构、历史对话、报错信息。喂得准，它就答得准。
权限决定它能碰什么、哪些动作必须先问你。这是 Harness 里唯一不能省的安全机制。

先认识两个最主流的

Claude Code
Anthropic 出品，跑在终端里。读 CLAUDE.md 作为项目说明书。生态最成熟，插件和文档最多。
Codex
OpenAI 出品，同样跑在终端里。有终端版、桌面版、IDE 插件、网页版和云端版五个入口，本质是同一个东西。读 AGENTS.md。
AGENTS.md
两者都是「给 AI 看的 README」。2025 年底起它变成了跨厂商的开放格式，Codex、Cursor、Gemini CLI、Copilot 等二十多个工具都读它，写一份就够。

好消息是它们在互相兼容：Claude Code 从 2.1.277 起，如果仓库里只有 AGENTS.md 没有 CLAUDE.md，它会直接读 AGENTS.md。所以你先学哪个都行，不用纠结。

装一个

先装 Claude Code。如果你更习惯 ChatGPT 的界面，直接跳到本章末尾看 Codex 的装法。

# macOS / Linux / WSL
curl -fsSL https://claude.ai/install.sh | bash

# Windows（PowerShell）
irm https://claude.ai/install.ps1 | iex

# 装完先确认
claude --version
用原生安装器的理由

原生安装器会自动更新。用 Homebrew、WinGet 装的不会，得自己记得升级。新手最容易踩的坑就是三个月后版本太旧，行为和文档对不上。

第一次用，按这四步走

  1. 进到项目目录再启动。务必先 cd 到你要改的项目里，再运行 claude。它只在你当前所在的位置工作，在哪启动就管哪。

    cd ~/projects/my-app
claude

  2. 第一次会问「是否信任这个文件夹」。选信任。这一步之后它才允许读文件和跑命令。

  3. 先问，别先改。刚进一个新项目，先让它自己介绍自己。

    这个项目是做什么的？用了什么技术栈？

  4. 退出用 /exit。或者在空提示符下连按两次 Ctrl+D。

真正的工作循环：先看计划，再让它动手

新手最容易犯的错，是一上来就说「帮我把这个功能做了」，然后看着它一口气改了几十个文件，最后你根本不知道它改了什么。

正确的顺序是先要方案：

/plan 给首页加一个搜索框，能按课程名过滤

它会给出计划但不动手改。你看完觉得靠谱，再让它执行。也可以在启动时就锁成只读模式：

claude --permission-mode plan

这套「先计划、后执行」的流程是 OpenAI 官方在最佳实践里明确推荐的，理由很简单：看不懂的计划，不该被执行。

权限确认是安全带，不是麻烦

你每次看到它问「是否允许执行 xxx」，那是在问你一个问题：你允许我动你的电脑吗？

这不是多余的步骤。AI 能执行任意终端命令，一旦判断错，可能删掉文件、把你的密钥推到网上、或者连上一个不该连的服务器。这一层人工确认，是目前唯一可靠的安全兜底。

会话中按 Shift+Tab 可以在几种模式之间循环：

模式它能做什么什么时候用
plan只读。只能看文件、给方案刚开始一个新任务、不确定影响范围时
acceptEdits自动改文件，跑命令还会问你已经确认了方案，进入执行阶段
default / 手动改文件和跑命令都问处理不熟悉的仓库时
跳过权限全部不问，直接做只在一次性容器或虚拟机里用
新手不要跳过权限

Claude Code 有个 --dangerously-skip-permissions 参数，名字里就写了 dangerous。它存在的唯一合理场景，是在开完就扔的一次性容器里跑批处理。在自己电脑上用，等于把家里钥匙交给一个你没见过的人。

给它写一份项目说明书

每次都重新解释一遍项目很烦。Harness 支持一个 Markdown 文件，写在项目根目录，每次启动自动读取，团队成员共享。

工具文件名作用范围
Claude CodeCLAUDE.md 或 AGENTS.md当前项目，随仓库提交
CodexAGENTS.md当前项目，随仓库提交
Claude Code~/.claude/CLAUDE.md你自己的所有项目
Codex~/.codex/AGENTS.md你自己的所有项目

让工具帮你写第一版，比自己憋着强：

# Claude Code
/init

# Codex
/init

它会扫描项目，自动生成一份初始版本。之后你可以手动补充成这样：

# AGENTS.md

## 怎么跑起来
- 安装依赖：npm install
- 开发服务器：npm run dev（http://localhost:3000）
- 测试：npm test
- 提交前必须跑：npm run lint

## 约定
- 2 空格缩进，单引号
- 不要改 src/generated/ 下的文件
- 不要提交 .env 里的任何内容
写说明书的两条原则

第一，写可验证的事实，不要写形容词。写「2 空格缩进」而不是「代码风格良好」。第二，别把它写太长，超过 200 行它会只读一部分。一次性操作流程写成 Skill（下一章），别塞进这里。

顺手：让它在独立副本上干活

如果你想同时做两件事，Claude Code 支持 worktree——给这次会话开一份独立的代码副本，在另一个分支上，互不干扰：

claude --worktree feature-login

文件会放在 .claude/worktrees/feature-login/。适合「让 AI 改 A 功能，你同时改 B 功能」这种并行场景。团队多人同时开发时也建议这么干。

那 Codex 怎么装

如果你更习惯 ChatGPT 的界面，那就用 Codex。有五个入口，本质是同一个东西：

入口形态适合
Codex CLI终端主力，和 Claude Code 同一类
ChatGPT 桌面版左上角菜单里选 Codex已经在用 ChatGPT，不想换工具
Codex IDE 插件编辑器里习惯在 IDE 里写代码
Codex 网页版浏览器 chatgpt.com/codex临时用
Codex CloudOpenAI 的云端机器关掉电脑也能继续跑，需要 Plus 及以上
 
# macOS / Linux（官方推荐）
curl -fsSL https://chatgpt.com/codex/install.sh | sh

# Windows（PowerShell）
powershell -ExecutionPolicy ByPass -c "irm https://chatgpt.com/codex/install.ps1 | iex"

# 登录（推荐用 ChatGPT 账号，不用单独买 API key）
codex login

# 然后照旧 cd 到项目里再运行
cd ~/projects/my-app
codex
一个真实的坑：别装错包

如果你用 npm，必须带 @openai/ 前缀：npm install -g @openai/codex。写成 npm install -g codex 会装到一个 2011 年的同名静态站点生成器上，而它装完之后 codex 命令居然能正常执行——很多人就这么以为自己装成功了。

Codex 里新人最该记的几个斜杠命令：/init（生成 AGENTS.md）、/plan（先规划）、/review（审查改动）、/permissions（设权限）、/status（看状态）。终端里还有 codex exec 和 codex review 两个非交互命令，写脚本和 CI 时用。

Chat、Work、Codex、Dots 到底什么关系

OpenAI 现在把 AI 分成了几个入口，名字很容易混。判断方法很简单：看你最后要的是什么。

入口做什么你要的成品是
Chat提问、搜索、头脑风暴一个答案
Work研究、整理分析文档、表格、演示、报告
Codex写调试代码、跑测试命令、看仓库代码改动、diff、测试结果
Dots常驻智能体，在你不在时跨应用持续推进一堆后台任务的结果

需要说明的是：Work 和 Codex 的能力是重叠的。官方原话是「Codex remains dedicated to software development」，Work 也能写代码。区别在界面习惯、技术细节的呈现方式，以及你最后要审的是文档还是 diff。

Dots 是什么，值不值得你关注

Dots 是 OpenAI 在 2026 年 9 月 29 日 DevDay 上发布的常驻智能体。它有自己的云端电脑和浏览器，能连 4000 多个应用，在你睡觉时继续干活，需要你时用文字或语音找它。

但今天（2026 年 10 月）不建议你碰它，有三个硬性原因：① 它只在 Pro $100 以上、Business Premium 和 Enterprise 开放，Plus 和免费版都用不了；② 官方在三处都写着「rolling out gradually」，还在分批推送，你所在的地区大概率还没轮到；③ 它编码时调用的其实就是 Codex 的云端环境——它是调度层，不是编码器。

一句话：想「让 AI 帮我写代码」，用 Codex，Plus 就够。Dots 是给需要 AI 在自己不在场时持续干活的人准备的，不是新手的起点。

本章要点

  • 只用网页版聊天，AI 碰不到你的项目。要动手就得用 Harness。
  • Claude Code 和 Codex 选一个就行，不用两个都学。它们共享 AGENTS.md 格式。
  • 先 /plan 拿方案，确认后再执行。
  • 权限确认别关。它是 AI 能跑在你电脑上的唯一安全带。
  • 项目的长期规则写进 AGENTS.md，别每次重新讲一遍。
04 / SKILL·MCP第四章 · Skill 与 MCP：给它装上手脚

目标：分清 Skill 和 MCP 到底是什么、各自解决什么问题，以及什么时候真的需要它们。

先分清这两样东西

这是最容易混的一对。用一句话区分：

Skill 是「经验」告诉 AI 做这类事要按什么流程走。它是文字，不给它新能力，但让同一件事每次做法一致。
MCP 是「接口」给 AI 接上一套新的工具或数据源，比如你的数据库、公司 API、某个网页。有了它，AI 才知道那些东西存在。

再举两个具体例子：你要做「每次发版后自动写更新公告」，这是 Skill——它规定了步骤和格式。AI 想查「上周有多少人投诉了退款」，这是 MCP——它需要一个能读你工单系统的接口。

Skill：把重复说的话存起来

如果你发现自己每次都要给 AI 贴同一段说明，或者每次都重复同一套步骤，那就该做成一个 Skill。

一个 Skill 就是一个文件夹，里面放一个 SKILL.md：

~/.claude/skills/summarize-changes/SKILL.md

放在项目里让全队共享的话，路径是 .claude/skills/<名字>/SKILL.md，跟着仓库一起提交。目录名就是命令名。

最小可用的内容长这样：

---
description: 总结当前未提交的改动并标出风险。当用户问改了什么、要提交信息、或者要 review diff 时使用。
---

## 当前改动

!`git diff HEAD`

## 要求

用两三句话总结上面的改动，然后列出你注意到的风险，
比如缺少错误处理、写死的值、需要同步更新的测试。
如果 diff 是空的，就说明没有未提交的改动。

有两处值得注意：

  • description 决定它什么时候自动触发。写得越具体，触发越准；写「帮助用户」这种等于没写。
  • !`git diff HEAD` 是动态注入：加载时真的会去跑这条命令，把输出嵌进上下文。省得每次都把 diff 贴进去。

触发方式有两种：AI 觉得匹配了就自动用；或者你直接打 /summarize-changes。

什么时候该做 Skill

就一条判断标准：同一段话你第三次打出来的时候，就该把它存成 Skill 了。反过来，如果一件事只做一次，写成 Skill 是浪费。

MCP：接上外部世界

MCP 全称 Model Context Protocol，由 Anthropic 在 2024 年 11 月开源提出。打个比方：以前每个 AI 工具要接 Slack、GitHub、数据库，都得自己写一套适配代码。MCP 把它变成了一个通用接口——像 USB-C 一样，插上就能用。

它的结构长这样：

   你 / AI
      │
      ▼
┌──────────────┐   JSON-RPC   ┌──────────────┐
│  MCP Client  │ ◄──────────► │  MCP Server  │
│ (Claude Code)│              │ (提供工具)    │
└──────────────┘              └──────────────┘
                                    │
                                    ▼
                            数据库 / API / 文档

Server 那头会提供三类东西：

类型是什么类比
Tools可以执行的函数，比如「查数据库」「发消息」手
Resources只读的数据，用 @server:uri 引用眼睛
Prompts预设的提示模板，会出现在斜杠命令里剧本

加一个 server 很简单，本地的用 -- 分隔，这个横杠不能漏，漏了它会把参数解析错：

# 远端 HTTP server（OpenAI 官方推荐的方式）
claude mcp add --transport http notion https://mcp.notion.com/mcp

# 本地 stdio server
claude mcp add --env API_KEY=xxx --transport stdio mydb \
  -- npx -y some-mcp-server

# 管理
claude mcp list
claude mcp remove mydb

官方提供的 server 覆盖了 Google Drive、Slack、GitHub、Git、Postgres 这些主流数据源，社区还有大量现成的。加的时候记得选好范围：--scope project 会写进项目里的 .mcp.json 跟着仓库共享，--scope user 只对你自己生效。

大部分人其实不需要 MCP

新手的项目基本是纯代码，没有外部数据源要接。Codex 和 Claude Code 自带的文件读写、命令执行、网页搜索已经够用了。等你真的遇到「AI 需要查一个它接触不到的系统」时再装，否则只是在给自己增加配置和排错成本。

安全问题

接进来的 server 能看到你授权的一切。新装的 server，先只给它最小必要的权限，看清楚它到底要访问什么，再决定要不要放宽。

本章要点

  • Skill 管「怎么做」，MCP 管「能碰到什么」。前者是文字，后者是接口。
  • 同一段话打第三次，就该存成 Skill。
  • MCP 等真正需要时再装。原生能力已经能覆盖大多数场景。
05 / PROMPT第五章 · 提示词：怎么把话说清楚

目标：掌握一套能重复使用的写法，让 AI 的输出稳定地达到你要的结果，而不是靠反复重问碰运气。

同一句话，效果可以差很远

这是新手最常见的困惑：明明我说了要干什么，它怎么还是做错？

原因通常不是模型笨，而是你省略了你自己脑子里默认存在、但没写出来的信息。你说「帮我加个搜索框」，它面对的是几百种可能——搜什么字段、放在哪、什么样式、搜不到显示什么、要不要防抖。这些你都没说，它只能猜。

提示词的本质不是「把话说得客气点」，而是把你脑子里的上下文补齐，让它不用猜。

四要素：目标、背景、约束、完成标准

这是 OpenAI 官方最佳实践里给的框架，也是最值得背下来的一个：

目标 Goal要什么。做成之后用户能做什么。
背景 Context在哪做。哪些文件、哪段报错、什么技术栈。
约束 Constraints怎么算符合要求。风格、不能动什么、安全要求。
完成标准 Done when怎么验证做完了。可检查的条件，而不是「做好了」。

同一个需求，两种写法：

不够好的写法

帮我给首页加个搜索框

加上四要素

目标：首页加一个课程搜索框。
背景：在 index.html 的 hero 下方，课程数据来自 courses.js。
约束：沿用现有 lilac 配色，不引入新依赖。
完成：输入即过滤，无结果显示「没有匹配的课程」。

右边这版会一次就对得多。写提示词的成本，永远低于返工的成本。

比「一句话需求」更好用的三个做法

  • 让它反过来问你。需求模糊时，别硬凑成一句长的。直接说「先别动手。问我几个问题，把需求问清楚再来做」。它问你答，五分钟胜过猜半小时。
  • 一次只推进一小步。「先把这个改完，跑起来给我看」比「把这个项目重写一遍」成功率高得多。做完一步看一步，方向不对时损失还很小。
  • 不认可就直说，别含糊。「不太对」对它是无效输入。说清楚哪里不对：「按钮位置不对，应该在搜索框右边而不是下面」。

长期规则别塞进提示词

如果你每次都要重复「本项目用 2 空格缩进」「不要动 src/generated」「提交前跑 lint」——这些不该反复说，该写进上一章讲的 AGENTS.md。提示词是一次性任务的说明，AGENTS.md 是常驻规则。混在一起的结果是提示词越来越长，AI 反而抓不住重点。

会话太长时还有两个命令可以救急：/clear 直接清空重新开始，/compact 把之前的对话压缩成摘要，保留进度但省出空间。

一个必须纠正的误解

在提示词里加一句「注意安全」，是没用的

这是很多人的直觉：既然 AI 写的代码不安全，那我在提示词里强调一下安全就行了。实测证明这条路走不通。一项基于 186 个真实任务的基准测试（arXiv:2512.03262）发现，表现最好的一组智能体有 57% 的方案功能正确，但只有 11.8% 是安全的；而在需求里加上漏洞提示并没有改善这一结果。

安全不是提示词能解决的事。真正要做的是第六和第七章讲的东西：用 Git 留下回滚能力，用测试和人工审查把住最后一道关。

别指望一次说对

最后一点心态上的建议：把跟 AI 的对话当成带一个很聪明但不了解你项目的实习生。它知识面极广，但不知道你们的规矩；而且它不会因为怕你尴尬就承认自己没听懂。

所以：给上下文、给例子、给反馈、随时纠偏。这是把工作做好的流程，不是话术。

06 / GIT第六章 · Git 与 GitHub：团队的公共记忆

目标：搞懂 Git 和 GitHub 是什么、为什么对团队协作的提升大到值得专门学一章，并掌握日常够用的那一小撮命令。

为什么这件事值得单独一章

前面五章都在讲怎么让 AI 帮你写代码。但 AI 写出来的东西如果只存在某一个人的电脑里，那它约等于不存在。换台电脑就没了，别人改坏了你回不去，两个人同时改必然冲突。

Git 解决的正是这件事。技术部反复验证过的一点是：同一个仓库能把三个人的协作效率拉高一个量级，原因不是它多聪明，而是它把下面几件事变成了默认行为：

  • 所有人的改动都有记录——谁在什么时候改了哪一行、为什么改，都能查到。
  • 改错了能退回去——这是新手最需要、也最容易获得的安全感。
  • 多人同时做不打架——靠分支把工作隔开，靠 Pull Request 合并。
  • 交接不再是问题——任何人拉下最新代码就能接着做，不依赖某个人的记忆。
和 AI 一起用，价值更大

官方最佳实践里明确建议：每个任务开始前和结束后各建一个 Git 检查点。因为 AI 一次能改几十个文件，一旦方向跑偏，没有回滚能力就只能手工一条条撤。有了检查点，一句 git reset --hard 就回到干净状态，可以放心让它大胆试。

五个概念，够用了

仓库 repository
一个项目的全部文件 + 全部历史记录。可以理解成一个带完整存档的文件夹。
提交 commit
一次存档点。记录改了哪些文件、改成什么样、谁改的、为什么改。
暂存区 staging
提交前的草稿区。git add 放进来，git commit 才正式存档。可以只提交一部分改动。
分支 branch
一条平行的时间线。开一条分支改东西，不影响主线；改完再合回去。主线通常叫 main。
远程 remote
托管在 GitHub 上的那份仓库副本，一般叫 origin。你和队友之间的同步全靠它。

日常够用的命令

不需要背全部。下面这十几条覆盖了 90% 的场景：

命令干什么
git clone <地址>把远程仓库完整复制到本地
git status看现在改了什么、在哪个分支。不确定时就先敲这条
git add <文件>把改动放进暂存区（git add . 是全部）
git commit -m "说明"把暂存区的内容正式存档
git log看历史记录
git diff看具体改了什么
git switch -c <名字>新建一条分支并切过去
git switch <分支>切到已有分支
git pull拉取队友的最新改动并合并进来
git push把你的提交上传到远程
git restore <文件>撤销某文件的改动（未提交时用）
git restore --staged <文件>从暂存区撤回，但保留改动

一次完整的工作

  1. 拿到最新代码。每次动手前先拉一次，别在旧版本上改。

    git pull

  2. 开一条自己的分支。不要直接在 main 上改。

    git switch -c feature/search-box

  3. 改代码。这里是让 AI 上场的时候。改完 git status 看一眼改了哪些文件。

  4. 提交。一次提交只做一件事，说明写清楚改了什么。

    git add .
git commit -m "feat: 首页加课程搜索框"

  5. 推到 GitHub，开 Pull Request。

    git push -u origin feature/search-box

Pull Request：团队协作的核心

PR 的意思是「我改好了，请你们看一下再合并」。它是整个 GitHub 协作流程里最有价值的一环：

  • 有人帮你看。合并之前有人能发现 bug、指出写得不好的地方、统一风格。
  • 讨论留在原地。所有评论都记在 PR 里，以后能查到，不用翻聊天记录。
  • 可以跑自动检查。测试、代码检查、安全扫描能自动跑，不通过就不让合并。
  • 保护主线。设成「必须走 PR 且至少一人批准才能合并」，就没人能直接把坏代码推到 main 上。

如果你是技术部新成员，记住一条就行：不要直接往 main 上提交，一定要走分支和 PR。这条规则存在的意义，就是让任何人都能放心往仓库里提交东西。

.gitignore：不该进仓库的东西

项目根目录放一个 .gitignore，告诉 Git 哪些文件不要管：

node_modules/
dist/
.env
.DS_Store
.vscode/

最关键的是 .env 和各类密钥文件。带密码的代码一旦推到公开仓库，等于公开发布了。

新手最容易踩的三个坑

一、force push 会抹掉队友的提交

git push --force 会用你本地的历史强行覆盖远程，可能把别人刚推的东西直接抹掉。万不得已要用，请用 git push --force-with-lease，它会先检查远程有没有别人的新提交。

二、在 main 上写了半天才发现有分支更合适

git switch -c 正确分支名 先建好分支（改动会跟着你过去），再考虑怎么处理已经提交的记录。新手阶段直接 git switch -c 就够了，历史不用动。

三、密钥推上去了

先立刻吊销或重置那个密钥——只删文件是不够的，历史里还在。公开仓库里的密钥应当直接视为已泄露。然后用 git filter-repo 重写历史并强制推送（私有仓库才可这么补救）。

现在就能学会的

不用一次全学。先把这四条练到不用想：git status、git add、git commit、git push。加上「不在 main 上直接改」这一条习惯，你就已经能安全地参与团队协作，剩下的用到再查。

写在最后HOW TO VIBE WELL

怎么成为一个
好的 vibe coder。

Vibe coding 这个词来自 Karpathy 在 2025 年 2 月的一条推文。他的原话值得完整看一遍，因为很多人只记住了前半句。

「我完全跟着感觉走，拥抱指数增长，甚至忘了代码的存在。我永远点 Accept All，已经不看 diff 了。代码增长到了我理解不了的程度……对于扔掉也无所谓的周末项目来说，这不算太糟。」

注意最后半句：提出这个词的人，一开始就说了它不适合正经项目。而且他描述的本来就是一个失控状态——代码超出自己的理解范围。

所以真正的问题不是「要不要 vibe coding」，而是：怎么用它的速度，同时不落到「代码没人能维护」的地步。

独立研究者 Simon Willison 给了一条非常实用的标准：

如果我不能向别人准确解释这段代码在做什么，我就不会把它提交进我的仓库。

这不是说新手必须看懂每一行——那不现实。而是说你得知道它在做什么、能回退、出了错能修。达不到这个标准之前，把代码当成草稿，别当成产品。

风险是真实存在的，不只是理论担忧

一项对 200 个已上线应用的安全审计（arXiv:2606.23130）发现：91% 至少含一个漏洞，其中三分之二属于严重或高危级别，集中在访问控制失效、注入和认证缺失。另一项 186 个真实任务的基准测试（arXiv:2512.03262）发现：功能正确的方案里有 57%，但安全的只有 11.8%。

结论不是「别用 AI 写代码」，而是：功能跑通不等于可以上线。

下面这六条，是把前面六章压缩之后留下的部分。刚开始做的时候，先照着做，做熟了再慢慢内化成习惯。

01

用 AI 提速度，不用它替你负责

它可以写得很快，但出了事是你在承担。「先跑起来」阶段可以不看每一行；「要给用户用」阶段必须能解释、能验证。

02

先看计划，再让它动手

一句「先别写，给个方案」能省掉大量返工。看不懂的计划不该被执行。

03

每个任务前后都留检查点

用 Git 存档。这是 AI 时代最该先学会的习惯——它让「大胆试」这件事变得安全。

04

规则写进 AGENTS.md，别靠记忆

人和 AI 都需要一份长期说明书。团队里这份文件本身就是最好的新人文档。

05

让它自证，而不是你信它

别停在「它说写好了」。要求它跑测试、跑起来给你看、检查 diff。功能正确和安全是两件事。

06

代码最终要交给人

GitHub 仓库是这个工作里最重要的资产。它让任何人（包括三个月后的你）能看懂、改得动、接得下去。
