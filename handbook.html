01 / 关于AI第一章 · 关于 AI

目标：把 LLM、Harness、Agent 这三个在 2026 年反复出现的概念讲清楚，并列出本方向最常用的一些编程语言。读完你应该能回答一个问题——为什么光有 ChatGPT 还不够？

一、LLM：会说话，但不做事

LLM（Large Language Model，大语言模型）是基于 Transformer 架构、在海量文本上预训练出来的概率模型。它的工作方式很朴素：给它一段上下文，它预测下一个词，然后把这个词接上去，再预测下一个，如此往复。

听起来太简单了，但正是这个简单的机制，产生了今天你看到的几乎所有 AI 能力。它生成的与其说是「正确答案」，不如说是「最像合理继续的文本」。

这个区别很重要，它解释了 LLM 的两个根本特性：

  • 它不查资料。它不知道今天几号、不知道你公司内部的文件写了什么、不知道某个库上周刚改过 API。它只是根据训练时见过的模式往下接。所以它会一本正经地编造 API、编造文献、编造不存在的函数。
  • 它不保证正确。凡是需要精确、确定、可重复的任务（算 1000 位乘法、统计某个文件有几行、调用一个它没见过的接口），它都不可靠。

好消息是，2026 年的主流 LLM 已经普遍具备下面这些能力：

长上下文能一次读进几十万到上百万 token，等于把一整个项目装进一次对话。
工具调用模型能输出「我要调用这个函数、参数是这些」的结构化请求。这是它能动手的前提。
多模态不只读文字，还能看图、听音频、看视频片段。
结构化输出能稳定地输出 JSON 或代码，而不只是散文。
但这些能力本身还不等于「Agent」

它们是 Agent 用来做决定的大脑。一个只会想、不会动、也没有人替它兜底的大脑，还算不上能干活。

二、Harness：给大脑接上身体

LLM 本身是无状态的——它不记得上一次你说了什么（除非你把历史再贴一遍），不会主动去调工具，也保证不了自己写出的代码真能跑起来。

把这些事补上的那层基础设施，就叫 Harness。2026 年最流行的一句总结是：

Agent = Model + Harness

判断一个东西算不算 Harness，有四个必要条件（arXiv 2606.10106）：

① Agent Loop推理 → 行动 → 观察结果 → 再推理的循环。关键在「观察」：每做完一步都要拿到真实反馈，而不是一口气写完就交差。
② Tool Interface让模型能真实地感知和修改外部环境：读文件、写文件、跑命令、访问网络。没有工具，模型只能输出文字。
③ Context Management决定每一轮把哪些内容喂给模型。项目结构、历史对话、报错信息，喂得准它才答得准。
④ Control Mechanisms不依赖模型「愿不愿意服从」的限制：沙箱、权限、验证器、确定性检查。这是唯一不指望模型自律的安全层。

哪些是 Harness，哪些不是

这几个概念很容易混。看一张表就清楚了：

类别是什么例子
模型负责思考和生成Claude、GPT、Gemini、DeepSeek
Harness把模型包起来，让它能真的干活Claude Code、Codex、opencode、Hermes Agent
框架造 Harness 的工厂，你自己动手搭LangGraph、CrewAI、AutoGen
SDK / 零件造 Harness 要用的零件库Claude Agent SDK、OpenAI Agents SDK

所以当你看到「XX 框架」「XX SDK」时，它不是一个能直接用的工具，你还得自己把四个必要条件搭齐。而 Claude Code 这种开箱即用的，才是 Harness。

三、Agent：跑起来的完整系统

Agent 是「模型 + Harness」组合之后跑起来的形态。给定一个目标，它自己决定下一步做什么、调哪个工具、怎么验证结果，一直干到目标完成或触发停止条件。

它和另外两种东西的区别，核心在自治度：

形态它做了什么谁在决定下一步
聊天机器人回答一次人问一句，它答一句
RAG 检索增强先检索资料，再生成回答流程写死，人来触发
Agent检索、决策、执行、观察、再决策，循环往复模型自己

2026 年主流 Agent 的四个角色

Planner 规划
把大目标拆成一个个能独立完成的小目标。
Executor 执行
在当前状态下决定调用哪个工具的那次 LLM 调用。这里是 token 消耗的大头。
Memory 记忆
短期 = 上下文窗口里的对话缓冲；长期 = 向量库、结构化数据库，或者就是你硬盘上的文件。
Tools 工具
网页搜索、代码解释器、数据库查询、文件操作、API，甚至另一个 Agent。

Anthropic 在 2024 年 12 月的《Building Effective Agents》里还做了一个更细的区分：Agentic Workflow（开发者预先画好流程图，LLM 只在节点里填内容）和 AI Agent（LLM 在运行时自己决定走流程图的哪条边）。前者更可控，后者更灵活，但更难预测。

这一章最重要的一句话

模型只会「说」，Harness 让它能「做」。记住 Agent = Model + Harness，第三章讲的就是 Harness 到底长什么样、有哪些、该怎么选。

03 / HARNESS第三章 · Harness：让 AI 真正动手

目标：搞清楚 Harness 是什么、现在到底有哪些、每个怎么用、有什么优缺点，以及怎么挑一个适合自己的。

一、先回到那句话

上一章的结论是：Agent = Model + Harness。模型是脑子，Harness 是身体。

你在 ChatGPT 网页框里聊天的时候，那基本只有一个脑子——能想、能写，但碰不到你硬盘上的任何东西。而 Claude Code、Codex、opencode 这类工具才是完整的身体：它们能读你项目里的文件、能改代码、能在终端里跑命令、能把报错信息再读一遍，然后自己决定下一步怎么办。

所以这一章要回答的是：这些身体现在有多少个？分别长什么样？该选哪个？用了有什么代价？

先说结论中的结论：如果你是零基础，Claude Code 和 Codex 这两家的桌面端都很好用，图形界面、不用碰终端，二选一即可。剩下的等你有需要再看。

二、现在的 Harness 有哪些

2026 年这个赛道非常拥挤，而且变动极快。先按「钱怎么花」分三类，这决定了它们的性格：

开源 + 自托管OpenHands、Hermes Agent连模型都可以自己部署。控制力最强，门槛也最高

  • Windsurf——2025 年 7 月被 Cognition 收购，作为独立产品已经不存在了，官网现在直接跳转到 devin.ai。

三、Claude Code：四种形态

Claude Code 是 Anthropic 的产品。它是闭源的——你装到的是一个编译好的二进制文件，看不到源码。但它有四种形态，而且是同一个引擎，配置、记忆、订阅全部互通，只在「界面长什么样、能干什么额外的事」上有差别。

这一点很重要：你不需要在四种里做单选题。它们是同一个大脑的四个窗口，用同一份订阅、同一套配置，随时可以换。

形态 A命令行版（CLI）

在终端里运行 claude，它直接读你的文件、改文件、跑命令。装法在后面「上手」那一节有。

除了日常对话，它还有两个能力是别的地方没有的：

  • 一次性非交互模式（headless）：-p 让它跑完一个任务就退出，适合写进脚本或者 CI。 
    # 跑一次就退出
claude -p "解释这个函数在做什么"

# 限制轮次和花费，防止跑飞
claude -p --max-turns 3 --max-budget-usd 5.00 "检查有没有语法错误"
  • 手机远程遥控：claude remote-control 之后，你可以在手机上看着并回复这个会话。需要说明的是——它一直跑在你自己的电脑上，手机只是个查看和回复的窗口，你的代码和文件系统没有离开本机。这和「Claude Code on the web」不是一回事，后者跑在 Anthropic 的云端。

什么时候用命令行版：你在用 SSH 连服务器、在容器里、或者想写脚本批量跑任务。这三种情况命令行版是唯一选择。反过来，如果你看见终端就头疼，那就别用。

形态 B桌面端（Code 标签）

很多人以为「Claude Code 只是个命令行工具」，这是误解。它有桌面应用，准确说是 Claude Desktop 里的 Code 标签页——同一个应用里有三个标签：Chat（普通聊天）、Cowork（长时间的自主任务）、Code（写代码，你要找的在这个里）。

最关键的一点：桌面端能直接读写你电脑上的项目文件，不是只能生成代码让你复制粘贴。选一个 Environment（Local / Cloud / SSH / WSL），指定项目文件夹，它就在真实的环境里干活。

它比命令行版多了这些图形化能力：

Diff 审阅改动逐个文件显示，可以点某一行直接写评论，它读到评论再去改。这是命令行版没有的。
内置终端和 Claude 共享同一环境，跑 npm test 看到的是同一批文件。
文件编辑器点路径直接改、保存回磁盘。
分屏布局对话、diff、终端、浏览器、文件任意拖拽排列，还能弹成独立窗口。多任务并行时很关键。

会话能不能在两端接着聊？能，但要注意规则：两边共享 CLAUDE.md、MCP、Skills、设置这些配置，但各自维护自己的会话列表。会话可以用 /desktop 从命令行搬进桌面端，也能从桌面端捡回命令行——搬的是同一个会话，不是副本。

桌面端没有的：它是纯交互的，没有 -p 那种非交互模式，所以不能写进 CI。另外它默认只连 Anthropic 自己的模型，不能切到第三方。

什么时候用桌面端：你不想碰终端、想一次开几个任务并行做、想图形化看 diff。这三种情况它明显比命令行版舒服。零基础强烈建议从桌面端开始。

形态 CIDE 插件（VS Code / JetBrains）

在编辑器里直接用。VS Code 上它是官方推荐的方式：内联 diff、计划审查、用 @ 引用你选中的几行、能翻历史会话。适合「我本来就整天开着 VS Code 写代码」的人。

形态 D云端（claude.ai/code）

跑在 Anthropic 的服务器上，关掉本地电脑也在跑。适合长任务。代价是它看不到你本地的东西——你得把项目传上去，而且它在上面也用不了你本地的 MCP 和工具。

四、Codex：同样四种形态

Codex 是 OpenAI 的产品，CLI 部分是完全开源的（Apache-2.0 协议，仓库在 github.com/openai/codex，用 Rust 写的）。这一点和 Claude Code 正好相反，值得知道。

它同样有命令行、桌面、网页、云端、IDE 插件，共用一份 AGENTS.md 和同一份登录凭据。

形态 ACodex CLI（命令行）

装好后在项目目录里运行 codex。它有两个非交互命令是重点：

  • codex exec——跑一次就退出，进度走 stderr，只有最终结果走 stdout，写脚本用这个。 
    codex exec "把这个函数改成异步并补上错误处理"

# 沙箱默认只读，要写文件得显式放开
codex exec --sandbox workspace-write "修复测试失败"

# 强制输出结构化 JSON
codex exec --output-schema schema.json "统计代码行数"
  • codex review——非交互式代码审查。可以针对未提交的改动、某个 commit、或者和某个分支的差异。

新手最该记的斜杠命令：/init（生成 AGENTS.md）、/plan（先出方案再动手）、/review（审查改动）、/permissions（设权限）、/status（看状态）。

形态 BChatGPT 桌面端里的 Codex

这一形态最容易被误解。官方原话是：Codex 在 ChatGPT 桌面应用里是一个「独立视图」。具体指三件事：

历史完全分开
你在 ChatGPT 里的聊天记录找不到 Codex 的对话，反过来也一样。Codex 有自己的侧边栏和历史。
不同步到网页和手机
Chat 和 Work 的历史在网页、手机、桌面之间是同步的，Codex 不会。手机上只能通过一个 Remote 标签看部分会话，而且那些不会变成手机上的聊天记录。
不是聊天功能
官方明确说它能操作本地文件夹、代码仓库、终端和开发工具。

补充一个背景：OpenAI 在 2026 年把原来独立的 Codex 桌面应用并进了 ChatGPT 桌面应用。合并的是外壳，不是历史——所以你在老文章里看到的「Codex App」，现在指的就是这个 Codex 视图。

什么时候用这个形态：你已经有 ChatGPT 订阅，想在一个图形界面里审 diff、同时盯几个任务，不想再装别的软件。

形态 CCodex Cloud（云端）

跑在 OpenAI 的云端机器上。你的电脑睡着甚至关掉，它照样在干活。你需要一个环境配置（选一个 GitHub 仓库，它自己装依赖、跑测试验证），发布之后就能反复起任务，每个任务有独立的工作区。

适合电脑要关、任务要跑很久、或者需要拿凭据访问私有服务的场景。注意：Codex Cloud 只能用 ChatGPT 账号登录，不支持 API key，而且要 Plus 及以上的套餐。

形态 DIDE 插件

支持 VS Code 系（VS Code、Cursor、Windsurf 这些编辑器）、Xcode 和 JetBrains。三个卖点是：能引用你当前打开的文件和选中的代码、就地看 diff 审改动、把长任务甩给云端。定位是「在你正在看的那段代码旁边干活」。

一个好消息：AGENTS.md 两边都能用

Claude Code 从 2.1.277 版起，如果项目里只有 AGENTS.md 而没有 CLAUDE.md，它会直接读 AGENTS.md。所以一个项目只维护一份说明文件就够，两家工具都认。

两个坑：① 如果 AGENTS.md 和 CLAUDE.md 同时存在，Claude Code 只读后者；② 加一个 CLAUDE.local.md 会静默地让 AGENTS.md 停止加载。所以最省心的做法是：只用 AGENTS.md，别建 CLAUDE.md。

五、其他几个值得知道的

除了上面两家主流的，还有几个在开源社区里很活跃的工具。了解它们有助于你看懂这个领域，但零基础暂时不用装。

opencode模型无关的开源 Harness

一句话：一个模型无关的开源 Harness，你想接哪家模型就接哪家。

它的特点是不绑定任何一家模型服务商——通过 Models.dev 支持 75 家以上，也能自己填任意 OpenAI 兼容端点，本地模型（Ollama、LM Studio、llama.cpp）也能接。由 Anomaly 公司开发，MIT 协议开源。

形态是终端界面（TUI）+ 桌面端 + 常见 IDE 的插件 + 网页版。它的规则文件也叫 AGENTS.md（同时兼容读取 CLAUDE.md）。

适合谁：想自由切换模型、或者想在同一个工具里同时用好几家模型的人。代价：你要自己准备 API key 并配置，开箱即用性不如订阅制产品。

注意别搞错：它和 OpenAI 没有任何关系，纯粹是名字撞了。GitHub 上还有一个同名的无关项目（Go 写的），已经归档改名了。

Hermes Agent会自己沉淀经验的常驻助手

先破除一个常见误解：Hermes Agent 不是模型，是 Harness。Nous Research 出了一系列叫 Hermes 的模型，也出了一个叫 Hermes Agent 的智能体外壳，两者是不同层面的东西——外壳可以换任意模型。

它和普通 coding agent 最大的区别在它会积累经验：普通 harness 每次会话都从零开始；Hermes Agent 会把做过的事自动整理成技能文件、记忆和用户画像，下次直接复用。注意这是文本层的改进，它不修改任何模型权重——另外它还能批量生成训练数据，去训练别家模型的工具调用能力。

它通过一个 gateway 进程接入了 20 多个平台（Telegram、Discord、Slack、飞书、钉钉、微信等），可以自己部署。

适合谁：想要一个长期在线、能从手机各个 App 找到的个人助手。不适合：只想安静写代码的人——它比纯 coding agent 重得多。

一个正好能说明「Harness ≠ 模型」的例子

Nous 官方文档明确写着：不建议在 Hermes Agent 里使用 Hermes 4 模型，因为 Hermes 4 是为「聊天和推理」调优的，不是为 Agent 依赖的那种高频工具调用循环调优的。同一个外壳，换个模型就不好用了——这就是模型和 Harness 是两回事的直接证据。

DSHDeepSeek 官方的开源 Harness

它确实存在，是 DeepSeek 官方做的开源 agent 外壳，仓库是 deepseek-ai/deepseek-harness，命令叫 dsh，MIT 协议，TypeScript 写的，2026 年 8 月发布。它的口号是「Everything is a Plugin」，架构上几乎所有东西都是插件。

形态有网页界面、桌面端、命令行和 Python SDK。和 DeepSeek 模型的关系要说明白：DSH 是外壳，不是模型——官方文档里从来没有出现 deepseek-chat 或 deepseek-reasoner 这两个名字。填入 DeepSeek 的 API key 就能用 DeepSeek 的模型，但它同时也能接 Claude、GPT、Kimi、GLM 等第三方模型，还支持自定义端点（OpenAI 和 Anthropic 两种协议都支持，所以 Ollama、vLLM 都能接）。

但是，重要提醒：它的仓库顶部写着一句 「THERE WILL BE COMPATIBILITY-BREAKING CHANGES」，安全文档里写得更直白——它没有经过安全审计，不能当作安全或可用于生产环境的软件。所有发布版本都还是 rc / alpha 阶段。

适合谁：想研究 agent 架构、想写插件、想用第三方模型跑 coding agent 的开发者。不适合：日常写代码，更不要用在生产环境。

按你的情况对号入座：

「本地运行」这个词有歧义，务必分清两层：

  • Harness 跑在哪——比如 Claude Code 桌面端选 Local 模式，程序跑在你电脑上。
  • 模型跑在哪——只要接的是云端模型，你的代码照样会发给模型服务商。

只有当你连模型也用本地的（Ollama、LM Studio 这类）时，代码才真正不离开你的电脑。用公司代码、同学的信息、或者任何涉及隐私的东西之前，先想清楚这一层。

七、装一个并跑起来

先装 Claude Code。如果你更习惯 ChatGPT 的界面，跳到本章末尾看 Codex 的装法。

# macOS / Linux / WSL
curl -fsSL https://claude.ai/install.sh | bash

# Windows（PowerShell）
irm https://claude.ai/install.ps1 | iex

# 装完先确认
claude --version

第一次用，按这四步走：

  1. 进到项目目录再启动。务必先 cd 到你要改的项目里，再运行 claude。它只在你当前所在的位置工作，在哪启动就管哪。

    cd ~/projects/my-app
claude

  2. 第一次会问「是否信任这个文件夹」。选信任。这一步之后它才允许读文件和跑命令。

  3. 先问，别先改。刚进一个新项目，先让它自己介绍自己。

    这个项目是做什么的？用了什么技术栈？

  4. 退出用 /exit。或者在空提示符下连按两次 Ctrl+D。

那 Codex 怎么装

# macOS / Linux（官方推荐）
curl -fsSL https://chatgpt.com/codex/install.sh | sh

# Windows（PowerShell）
powershell -ExecutionPolicy ByPass -c "irm https://chatgpt.com/codex/install.ps1 | iex"

# 登录：推荐用 ChatGPT 账号，不用单独买 API key
codex login

# 然后照旧 cd 到项目里再运行
cd ~/projects/my-app
codex

（如果 codex login 提示找不到命令，直接运行 codex，它第一次启动会引导你选登录方式，效果一样。）

一个真实的坑：别装错包

如果你用 npm，必须带 @openai/ 前缀：npm install -g @openai/codex。写成 npm install -g codex 会装到一个 2011 年的同名静态站点生成器上，而它装完之后 codex 命令居然能正常执行——很多人就这么以为自己装成功了。

八、权限：唯一的安全带

你每次看到它问「是否允许执行 xxx」，那是在问你：你允许我动你的电脑吗？

这不是多余的步骤。AI 能执行任意终端命令，一旦判断错，可能删掉文件、把密钥推到网上、或者连上一个不该连的服务器。这一层人工确认，是目前唯一可靠的安全兜底。

会话中按 Shift+Tab 可以在几种模式之间循环：

模式它能做什么什么时候用
plan只读。只能看文件、给方案刚开始一个新任务、不确定影响范围时
acceptEdits自动改文件，跑命令还会问你已经确认了方案，进入执行阶段
default / 手动改文件和跑命令都问处理不熟悉的仓库时
跳过权限全部不问，直接做只在一次性容器或虚拟机里用
新手不要跳过权限

Claude Code 有个 --dangerously-skip-permissions 参数，名字里就写了 dangerous。它存在的唯一合理场景，是在开完就扔的一次性容器里跑批处理。在自己电脑上用，等于把家里钥匙交给一个你没见过的人。

九、给它写一份项目说明书

每次都重新解释一遍项目很烦。Harness 支持一个 Markdown 文件，写在项目根目录，每次启动自动读取，团队成员共享。

工具文件名作用范围
Claude CodeCLAUDE.md 或 AGENTS.md当前项目，随仓库提交
CodexAGENTS.md当前项目，随仓库提交
opencodeAGENTS.md当前项目，随仓库提交
Claude Code~/.claude/CLAUDE.md你自己的所有项目
Codex~/.codex/AGENTS.md你自己的所有项目

让工具帮你写第一版，比自己憋着强——在会话里输入 /init，它会扫描项目自动生成一份。之后你可以手动补充成这样：

# AGENTS.md

## 怎么跑起来
- 安装依赖：npm install
- 开发服务器：npm run dev（http://localhost:3000）
- 测试：npm test
- 提交前必须跑：npm run lint

## 约定
- 2 空格缩进，单引号
- 不要改 src/generated/ 下的文件
- 不要提交 .env 里的任何内容
写说明书的两条原则

第一，写可验证的事实，不要写形容词。写「2 空格缩进」而不是「代码风格良好」。第二，别把它写太长，超过 200 行它会只读一部分。一次性操作流程写成 Skill（下一章），别塞进这里。

还有一个很顺手的能力：让它在独立副本上干活。如果你想同时做两件事，可以给它开一份独立的代码副本，在另一个分支上，互不干扰：

claude --worktree feature-login

文件会放在 .claude/worktrees/feature-login/。适合「让 AI 改 A 功能，你同时改 B 功能」这种并行场景。团队多人同时开发时也建议这么干。

十、Harness 的优缺点

前面九节都在讲怎么用。但这一节更重要——任何工具都有代价，你得知道付的是什么。

它确实很强的地方

  • 从「能聊天」到「能干活」的质变。这是最实在的一条。以前 AI 只能给一段代码让你复制粘贴，现在它能自己读文件、跑起来、看报错、再改——反馈闭环是质变，不是效率提升。
  • 上手门槛低到反常。会说话就能用。你不需要会写代码才能让 AI 写代码。
  • 长上下文让「整个项目」成为可能。把几十万 token 的代码库装进上下文，AI 理解项目的方式接近人。这是单个文件级的补全工具做不到的。
  • 可回滚性让大胆试变得安全。配合 Git 检查点，它一次改几十个文件也不怕——不行就退回去。
  • 生态在快速成熟。Skill、MCP、插件市场，几个月前还没有的东西现在已经能用了。

必须知道的缺陷

一、安全问题有实证数据，不是空谈

新加坡国立大学对 200 个已上线的 AI 生成应用做了安全审计（arXiv:2606.23130），发现 91% 至少含一个漏洞，其中三分之二属于严重或高危级别，集中在访问控制失效、注入和认证缺失。另一项基于 186 个真实任务的基准测试（arXiv:2512.03262）发现：功能正确的方案占 57%，但安全的只有 11.8%。

而且研究者特别指出：在提示词里加「请注意安全」并不能改善这一点。安全不是提示词能解决的事。

  • 二、它会为了「让错误消失」而破坏安全。上面那篇审计论文把这归为「目标缺陷」：当代码跑不通时，Agent 倾向于移除校验、放宽权限、绕过检查，而不是回头查原因。这和人的直觉相反——人卡住了会去想「为什么」，AI 更可能想「怎么绕过」。
  • 三、代码可能超出你的理解范围。这是最隐蔽的风险。Karpathy 提出「vibe coding」时就明说了这一点：代码增长到了自己理解不了的程度。代码能跑 ≠ 你能维护它。一旦三个月后出 bug，你连从哪里开始查都不知道。
  • 四、成本不可预测。订阅看着是月付的，但实际用量有「每 5 小时窗口」的额度限制，任务一多就容易撞上限。更麻烦的是如果误配成 API key 计费，那是按 token 单独收费的，跟订阅完全分开——一个跑飞的循环可能一天烧掉不少钱。用 API key 模式时一定要设预算上限。
  • 五、依赖网络和云服务。断网、云端故障、限流都会让它停摆。纯订阅制产品还带来厂商锁定：你的工作流、提示词习惯、Skill 资产都长在一家服务商上。
  • 六、会放大你原有的模糊。你说不清楚的需求，AI 也不会问清楚，它会猜。「先别写，问我几个问题」这个习惯能挡掉大部分返工。
  • 七、越新越不稳。前面说的 DSH 直接在仓库顶上写着「会有破坏性变更」，Aider 更新放缓，Roo Code 已经死了。选型时优先考虑活跃维护的开源工具，和有多个入口的大厂产品，能少踩很多坑。

怎么用才能扬长避短

四个原则
  • 从最不可信的任务开始。一次性脚本、个人小工具、探索性原型——这些地方它出错的代价最小，收益最大。
  • 权限从紧开始。官方最佳实践的原话是「Start with tight approval/sandbox settings, loosen only for trusted repos」。先从只读的计划模式开始，熟了再放开。
  • 不要只让它生成代码。要让它写测试、跑检查、确认行为、审查 diff。这是 OpenAI 官方指南里最该被记住的一句。
  • 每个任务前后建 Git 检查点。这不是可选项，是让「大胆试」这个动作成立的前提。详见第六章。

十一、常见坑

  • 装了个已经死了的项目。先看 GitHub 最后一次提交时间。
  • npm 装错包。见前面 Codex 那节的警告。
  • 在错误的目录启动。它只管当前目录。先 cd 再启动。
  • 一个会话干到底。聊了几十轮之后，早期的目标早就被挤出上下文了，它开始跑偏。一个会话干完一件事，然后开新的。
  • 把长期规则每次都重打一遍。写进 AGENTS.md，一次搞定。
  • 用 DSH 这类预览版做正式项目。它没经过安全审计。
04 / SKILL·MCP第四章 · Skill 与 MCP：给它装上手脚

目标：分清 Skill 和 MCP 到底是什么、各自解决什么问题，以及什么时候真的需要它们。

先分清这两样东西

这是最容易混的一对。用一句话区分：

Skill 是「经验」告诉 AI 做这类事要按什么流程走。它是文字，不给它新能力，但让同一件事每次做法一致。
MCP 是「接口」给 AI 接上一套新的工具或数据源，比如你的数据库、公司 API、某个网页。有了它，AI 才知道那些东西存在。

再举两个具体例子：你要做「每次发版后自动写更新公告」，这是 Skill——它规定了步骤和格式。AI 想查「上周有多少人投诉了退款」，这是 MCP——它需要一个能读你工单系统的接口。

Skill：把重复说的话存起来

如果你发现自己每次都要给 AI 贴同一段说明，或者每次都重复同一套步骤，那就该做成一个 Skill。

一个 Skill 就是一个文件夹，里面放一个 SKILL.md：

~/.claude/skills/summarize-changes/SKILL.md

放在项目里让全队共享的话，路径是 .claude/skills/<名字>/SKILL.md，跟着仓库一起提交。目录名就是命令名。

最小可用的内容长这样：

---
description: 总结当前未提交的改动并标出风险。当用户问改了什么、要提交信息、或者要 review diff 时使用。
---

## 当前改动

!`git diff HEAD`

## 要求

用两三句话总结上面的改动，然后列出你注意到的风险，
比如缺少错误处理、写死的值、需要同步更新的测试。
如果 diff 是空的，就说明没有未提交的改动。

有两处值得注意：

  • description 决定它什么时候自动触发。写得越具体，触发越准；写「帮助用户」这种等于没写。
  • !`git diff HEAD` 是动态注入：加载时真的会去跑这条命令，把输出嵌进上下文。省得每次都把 diff 贴进去。

触发方式有两种：AI 觉得匹配了就自动用；或者你直接打 /summarize-changes。

什么时候该做 Skill

就一条判断标准：同一段话你第三次打出来的时候，就该把它存成 Skill 了。反过来，如果一件事只做一次，写成 Skill 是浪费。

MCP：接上外部世界

MCP 全称 Model Context Protocol，由 Anthropic 在 2024 年 11 月开源提出。打个比方：以前每个 AI 工具要接 Slack、GitHub、数据库，都得自己写一套适配代码。MCP 把它变成了一个通用接口——像 USB-C 一样，插上就能用。

它的结构长这样：

   你 / AI
      │
      ▼
┌──────────────┐   JSON-RPC   ┌──────────────┐
│  MCP Client  │ ◄──────────► │  MCP Server  │
│ (Claude Code)│              │ (提供工具)    │
└──────────────┘              └──────────────┘
                                    │
                                    ▼
                            数据库 / API / 文档

Server 那头会提供三类东西：

类型是什么类比
Tools可以执行的函数，比如「查数据库」「发消息」手
Resources只读的数据，用 @server:uri 引用眼睛
Prompts预设的提示模板，会出现在斜杠命令里剧本

加一个 server 很简单，本地的用 -- 分隔，这个横杠不能漏，漏了它会把参数解析错：

# 远端 HTTP server（OpenAI 官方推荐的方式）
claude mcp add --transport http notion https://mcp.notion.com/mcp

# 本地 stdio server
claude mcp add --env API_KEY=xxx --transport stdio mydb \
  -- npx -y some-mcp-server

# 管理
claude mcp list
claude mcp remove mydb

官方提供的 server 覆盖了 Google Drive、Slack、GitHub、Git、Postgres 这些主流数据源，社区还有大量现成的。加的时候记得选好范围：--scope project 会写进项目里的 .mcp.json 跟着仓库共享，--scope user 只对你自己生效。

大部分人其实不需要 MCP

新手的项目基本是纯代码，没有外部数据源要接。Codex 和 Claude Code 自带的文件读写、命令执行、网页搜索已经够用了。等你真的遇到「AI 需要查一个它接触不到的系统」时再装，否则只是在给自己增加配置和排错成本。

安全问题

接进来的 server 能看到你授权的一切。新装的 server，先只给它最小必要的权限，看清楚它到底要访问什么，再决定要不要放宽。

本章要点

  • Skill 管「怎么做」，MCP 管「能碰到什么」。前者是文字，后者是接口。
  • 同一段话打第三次，就该存成 Skill。
  • MCP 等真正需要时再装。原生能力已经能覆盖大多数场景。
05 / PROMPT第五章 · 提示词：怎么把话说清楚

目标：掌握一套能重复使用的写法，让 AI 的输出稳定地达到你要的结果，而不是靠反复重问碰运气。

同一句话，效果可以差很远

这是新手最常见的困惑：明明我说了要干什么，它怎么还是做错？

原因通常不是模型笨，而是你省略了你自己脑子里默认存在、但没写出来的信息。你说「帮我加个搜索框」，它面对的是几百种可能——搜什么字段、放在哪、什么样式、搜不到显示什么、要不要防抖。这些你都没说，它只能猜。

提示词的本质不是「把话说得客气点」，而是把你脑子里的上下文补齐，让它不用猜。

四要素：目标、背景、约束、完成标准

这是 OpenAI 官方最佳实践里给的框架，也是最值得背下来的一个：

目标 Goal要什么。做成之后用户能做什么。
背景 Context在哪做。哪些文件、哪段报错、什么技术栈。
约束 Constraints怎么算符合要求。风格、不能动什么、安全要求。
完成标准 Done when怎么验证做完了。可检查的条件，而不是「做好了」。

同一个需求，两种写法：

不够好的写法

帮我给首页加个搜索框

加上四要素

目标：首页加一个课程搜索框。
背景：在 index.html 的 hero 下方，课程数据来自 courses.js。
约束：沿用现有 lilac 配色，不引入新依赖。
完成：输入即过滤，无结果显示「没有匹配的课程」。

右边这版会一次就对得多。写提示词的成本，永远低于返工的成本。

比「一句话需求」更好用的三个做法

  • 让它反过来问你。需求模糊时，别硬凑成一句长的。直接说「先别动手。问我几个问题，把需求问清楚再来做」。它问你答，五分钟胜过猜半小时。
  • 一次只推进一小步。「先把这个改完，跑起来给我看」比「把这个项目重写一遍」成功率高得多。做完一步看一步，方向不对时损失还很小。
  • 不认可就直说，别含糊。「不太对」对它是无效输入。说清楚哪里不对：「按钮位置不对，应该在搜索框右边而不是下面」。

长期规则别塞进提示词

如果你每次都要重复「本项目用 2 空格缩进」「不要动 src/generated」「提交前跑 lint」——这些不该反复说，该写进上一章讲的 AGENTS.md。提示词是一次性任务的说明，AGENTS.md 是常驻规则。混在一起的结果是提示词越来越长，AI 反而抓不住重点。

会话太长时还有两个命令可以救急：/clear 直接清空重新开始，/compact 把之前的对话压缩成摘要，保留进度但省出空间。

一个必须纠正的误解

在提示词里加一句「注意安全」，是没用的

这是很多人的直觉：既然 AI 写的代码不安全，那我在提示词里强调一下安全就行了。实测证明这条路走不通。一项基于 186 个真实任务的基准测试（arXiv:2512.03262）发现，表现最好的一组智能体有 57% 的方案功能正确，但只有 11.8% 是安全的；而在需求里加上漏洞提示并没有改善这一结果。

安全不是提示词能解决的事。真正要做的是第六和第七章讲的东西：用 Git 留下回滚能力，用测试和人工审查把住最后一道关。

别指望一次说对

最后一点心态上的建议：把跟 AI 的对话当成带一个很聪明但不了解你项目的实习生。它知识面极广，但不知道你们的规矩；而且它不会因为怕你尴尬就承认自己没听懂。

所以：给上下文、给例子、给反馈、随时纠偏。这是把工作做好的流程，不是话术。

06 / GIT·GITHUB第六章 · Git 与 GitHub：团队的公共记忆

目标：分两部分讲清楚——前半是 Git，解决「代码只存在我电脑上、并且能安全回退」；后半是 GitHub，解决「三个人怎么一起改同一个项目而不打架」。第二部分会讲得比较细，因为团队怎么具体协作是这一章最重要的地方。

第一部分 · Git：你电脑上的版本控制

五个概念，够用了

仓库 repository
一个项目的全部文件 + 全部历史记录。可以理解成一个带完整存档的文件夹。
提交 commit
一次存档点。记录改了哪些文件、改成什么样、谁改的、为什么改。
暂存区 staging
提交前的草稿区。git add 放进来，git commit 才正式存档。可以只提交一部分改动。
分支 branch
一条平行的时间线。开一条分支改东西，不影响主线；改完再合回去。主线通常叫 main。
远程 remote
托管在 GitHub 上的那份仓库副本，一般叫 origin。你和队友之间的同步全靠它。

日常够用的命令

不需要背全部。下面这十几条覆盖了 90% 的场景：

命令干什么
git clone <地址>把远程仓库完整复制到本地
git status看现在改了什么、在哪个分支。不确定时就先敲这条
git add <文件>把改动放进暂存区（git add . 是全部）
git commit -m "说明"把暂存区的内容正式存档
git log看历史记录
git diff看具体改了什么
git switch -c <名字>新建一条分支并切过去
git switch <分支>切到已有分支
git fetch origin只下载远端更新，不动你的文件
git pull拉取并合并队友的最新改动
git push把你的提交上传到远程
git restore <文件>撤销某文件的改动（未提交时用）
git branch -d <名字>删掉已经合并完的本地分支

fetch、merge、rebase、pull 到底什么区别

这是新手最容易混淆的一组。用一句话记：fetch 是「只看不碰」，pull 是「看完并合并」。

命令它做了什么会改我的文件吗
git fetch origin只把远端新提交下载到本地的 origin/main绝不
git merge origin/main把远端内容合并进来，产生一个合并提交会
git rebase origin/main把你的提交摘下来重放到最新主线之上，提交 ID 会变会
git pull origin main= fetch + merge，一步到位会
git pull --rebase origin main= fetch + rebase会

怎么选：

  • 「我想知道队友更新了什么，但不想动我的代码」→ git fetch origin，然后 git log HEAD..origin/main 看差异
  • 「把我这条分支更新到最新主线」，只有我在用这条分支→ git rebase origin/main，历史干净
  • 「把我这条分支更新到最新主线」，别人也在用这条分支→ git merge origin/main，不要改写别人的提交
  • 「我只是想让本地 main 最新」→ git switch main && git pull
rebase 的黄金法则

永远不要 rebase 一条已经推送到远端、且别人可能已经基于它工作的分支。rebase 会改写提交 ID，别人拉下来时历史会错乱。只有「我自己开的 feature 分支」才可以用 rebase。

.gitignore：不该进仓库的东西

项目根目录放一个 .gitignore，告诉 Git 哪些文件不要管：

node_modules/
dist/
.env
*.log
.DS_Store
.vscode/

最关键的是 .env 和各类密钥文件。带密码的代码一旦推到公开仓库，等于公开发布了，后面会讲怎么处理。

第二部分 · GitHub：团队的公共记忆

Git 只解决了「代码存在我电脑上」。接下来的问题只有 GitHub 能答：凭什么全队能改同一份代码？凭什么改错了能退回去？凭什么三个月后有人接手还看得懂？

为什么在 AI 时代反而更需要它

一个反直觉但很重要的事实：AI 让「写代码」变便宜了，于是「验证代码、归属责任、传递上下文、撤回错误」这四件事的相对成本上升了。GitHub 恰好就是这四件事的载体。

① 上下文AI 最大的失败模式不是写不出代码，而是不知道你们团队的规矩。仓库里的 AGENTS.md、README、CODEOWNERS 就是给人和 AI 共用的项目记忆——把口口相传的知识变成能提交、能评审、能交接的资产。
② 可审计GitHub 官方 2026 年 5 月的数据：新增代码约 41% 由 AI 辅助生成，超过五分之一的 code review 涉及 agent。当「生成一份看起来合格的 diff」成本趋近于零，而人的审查注意力固定不可扩容，review 就从「锦上添花」变成了整条链路上唯一的人类闸门。
③ 回滚Git 是唯一让「大胆试错」变便宜的东西。AI 在自己的分支上改，改坏了直接关掉分支，main 一行未动。这让「大胆方案」在期望值上真正可行。
④ 交接传统项目里作者和理解者之间有天然通信链路——作者还在，微信问一句就清楚了。AI 写代码打破了这个前提：作者是 Copilot，他不在群里。PR 描述、评论线程、git blame 就是替代品。
一句话总结

AI 时代不是让 GitHub 变得不重要，而是让它从「记录历史」变成了「分配责任」。GitHub 官方自己的说法是：「开发者永远拥有 merge 按钮，改变的是点下它之前发生的一切。」

另外有个值得知道的研究结论：Google DORA 2025 报告发现 AI 是放大器——它放大高效组织的优势，也放大低效组织的失能；吞吐量上升的同时，交付的不稳定性同样上升。该报告把「强版本控制实践」列为 AI 成功用法的七项基础能力之一。

机制 1Pull Request：整个协作的中枢

PR 的意思是「我改好了，请你们看一下再合并」。它不是「代码分享功能」，而是整个团队流程的中枢——评审、讨论、CI 检查、合并，全挂在它上面。

一次 PR 的完整生命周期：

  1. 开 PR（还没写完可以先开 draft，draft 不能被合并，也不会自动请求 review）

  2. CI 自动触发，必须全绿

  3. 请求评审（人可以手动选，CODEOWNERS 会自动指派）

  4. Reviewer 评论 / Request changes / Approve

  5. 作者改完再提交 → 之前的 Approve 可能被自动撤销（这是故意的，防止「批准后偷偷加代码」）

  6. 所有讨论线程 resolve → 满足全部规则 → 合并

最容易被忽略的机制：Request changes 是硬阻塞

GitHub 的 review 只有三种状态：Comment（纯反馈，不表态）、Approve（通过）、Request changes（要求修改）。只有第三种会真正阻止合并，而且它会一直生效——同事后来 push 了修复代码不会自动解除，你必须回去重新审一遍、或者他重新 Approve。

关联 issue

在 PR 描述里写 Closes #12，PR 合并进默认分支时对应的 issue 会自动关闭。但有个致命限制：PR 的目标分支必须是仓库的默认分支，否则关键词会被完全忽略。也可以在 PR 右侧的 Development 面板手动关联。

机制 2分支保护：让规矩没法被绕过

这是团队协作里投入产出比最高的一个设置——花 5 分钟配置，省掉后面无数麻烦。

它规定「什么情况下才允许合并进 main」，并且对所有人生效，包括管理员。仓库路径：Settings → Branches → Add rule。

要勾的规则它拦住了什么
Require a pull request before merging禁止直接往 main 推代码
Require approvals（设 1）防止自己写自己批
Dismiss stale approvals when new commits are pushed防止「批准后偷偷加代码」
Require conversation resolution防止「嘴上说改了，实际没改」
Require status checks to pass测试没过不许合
Require branches to be up to date防止带着一堆冲突去合并
Require linear history禁掉 merge commit，历史保持线性
Do not allow bypassing these settings管理员也不能开后门
Allow force pushes / Allow deletions保持关闭，这是防事故的最后一道闸

重要：配完之后，连仓库所有者自己也必须走 PR 才能改 main。这是故意的——如果连管理员都能绕过，那这个规则对其他人就只是建议。

「必需检查」最容易踩的坑

如果 PR 一直卡住、提示「等待检查通过」但你看不到任何检查：多半是检查名称和 CI 里的 job 名对不上。要么名字不一致，要么你忘了在规则里勾选对应的那个检查。这条规则是隐形的，GitHub 不会明确告诉你哪里错了，只能一个个对照 job 名找。

机制 3CODEOWNERS：指定谁必须看哪个文件

一个纯文本文件，告诉 GitHub「哪些文件归谁管」。当 PR 改动这些文件时，GitHub 自动向对应的人请求 review——不用谁记得去点。

放在 .github/CODEOWNERS，内容长这样：

# 注释用 #

# 全局默认负责人
*                    @你的组织/前端组

# 按文件类型
*.js                 @张三
*.css                @李四

# 按目录（前导 / 表示从仓库根开始）
/docs/               @张三

# 任意深度的同名目录
**/logs              @李四
三个必须知道的规则
  • 最后一条匹配的模式生效（和 .gitignore 一样），所以 * 要放最前面。
  • 同一模式的多个负责人必须写在同一行，写成两行的话第二行会覆盖第一行。
  • 只对默认分支上的 CODEOWNERS 生效。你在新分支上加的文件，对当前这个 PR 无效，得先合并上去才对以后的 PR 生效。

安全建议：把 CODEOWNERS 文件自己也保护起来——/.github/CODEOWNERS @负责人，否则别人可以改掉分工表。

机制 4GitHub Actions：让机器先过一遍

GitHub 内置的自动检查服务。你在 .github/workflows/ 放一个 YAML 文件，GitHub 就会在每次 push 或开 PR 时自动在一台干净的虚拟机上跑你指定的命令。

它把「测试跑没跑过」从作者的口头保证，变成页面上一个红绿勾——这是 review 之前最省事的自动化。

name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - name: 检出代码
        uses: actions/checkout@v4

      - name: 设置 Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: 安装依赖
        run: npm ci

      - name: 运行测试
        run: npm test

如果你的项目没有依赖任何东西（纯 HTML 页面），CI 不需要跑单元测试，光是「必需文件是否存在」「有没有误提交敏感文件」「HTML 结构对不对」这几项检查，就已经能拦住大部分低级错误，而且零依赖、不会因为环境问题假失败。

AI 时代最需要警惕的一件事：CI 作弊

GitHub 官方在 2026 年 5 月专门写过一篇 agent PR 的文章，其中点名一种失效模式：AI 为了让 CI 变绿，会删掉失败的测试、跳过 lint、或者在命令后面加 || true。官方的原话是：任何削弱 CI 的改动都是「一票否决」。

所以 review 时一定要先看有没有动 CI 配置和测试文件——这是 AI 写代码时代新增的一条红线，对人写的 PR 同样适用。

机制 5AI 在 GitHub 上扮演什么角色

2026 年的 GitHub 上已经有一整套 AI 功能，它们在团队流程里承担的角色各不相同：

角色它在哪一步你要做什么
补全 / 编辑本地 IDE 里照常写，改动还是你负责
规划（Plan Mode）写码之前回答它的澄清问题，确认计划
云端 Agent接一个 issue，后台干活审它开的 draft PR，决定合不合
自动 code reviewPR 打开时不能只信它，见下面的警告

GitHub 在设计上对 agent 做了不少限制，值得知道：它只能推送到自己创建的那一个分支（copilot/ 前缀），不能自己把 PR 标记为可合并，不能自己 approve，也不能自己 merge；并且指派人不能 approve 这个 agent 开出来的 PR——防止自审自批。

GitHub 自己对自动 review 的免责声明，原文大意

它可能漏掉代码里的问题（尤其改动大或复杂时），也可能报告根本不存在的问题；它给的建议未必正确，还可能含安全漏洞。官方原话是：「你始终应当审阅并验证 Copilot 生成的反馈，并用谨慎的人工审阅来补充它。」

换句话说：自动 review 是帮你筛出可疑点，不是替你把关。把机器的判断当作「值得看一眼的地方」，而不是「已经检查过了」。

团队具体怎么协作：从零到合并

这一节是本章的核心。下面是一条从开始工作到合并完成的完整路径，照着做就行。

第一步：每天开工，先同步

这是防冲突的第一道闸。不要在过期的代码上写新功能——否则你的 PR 会塞满和本次需求无关的 diff，reviewer 看不懂，合并时也更容易撞车。

git switch main
git pull origin main
git switch -c feat/12-login-page   # 基于最新的 main 开分支

第二步：写代码，分次提交

git status                  # 永远先看这个
git diff                    # 看具体改了什么

git add 具体文件路径          # 推荐：明确指定要提交什么
git commit -m "feat(auth): 添加登录表单组件"

commit message 建议用固定前缀，一眼能看出改动性质：

前缀含义
feat新功能
fix修 bug
docs文档
refactor重构，不改功能
chore杂务（依赖更新、配置）

第三步：推到 GitHub，开 PR

git push -u origin feat/12-login-page

然后在 GitHub 网页上开 Pull Request。描述里至少写清三件事：

不合格的描述

修了一些东西

合格的描述

做了什么：新增登录表单，接了 /api/login。
怎么验证：跑 npm run dev，打开 /login，用测试账号登录。
关联：Closes #12

还没写完就先开成 draft PR，等人看个方向；写完点 Ready for review，这时才会正式触发 review 流程。

第四步：PR 打开后，main 又更新了怎么办

这是新手最容易忽略的一步。如果不管，PR 会越拖越难合。

最简单的方式：PR 页面上会有蓝色提示条，点 Update branch 就行。

命令行（更可控）：

git switch main
git fetch origin
git merge origin/main        # 让本地 main 追上远端

git switch feat/12-login-page
git rebase origin/main       # 把你的提交搬到最新 main 之上
# 如果有冲突：解决后 git add . && git rebase --continue

git push --force-with-lease
只能用 --force-with-lease，永远不要用 --force

--force 无条件覆盖远端，会无声地抹掉同事刚推的提交。--force-with-lease 会先检查远端是不是还是你上次看到的那个版本，如果别人推过东西，它会直接拒绝并报错。这一个字母的差别，救过很多人的提交。

第五步：处理 review 意见

拿到意见之后，在同一个分支上继续改，不要为 review 意见新开 PR——这样 reviewer 能在同一个页面看到完整的对话历史。

回复评论时，说清楚「改了什么、为什么这么改、验证了没有」，而不是只回「好的，我改一下」——后者等于让人家自己再去看一遍 diff。

改完之后点评论线程下方的 Resolve conversation，把这条讨论标记为已解决。如果分支保护开了「所有对话必须解决」，没 resolve 会直接挡住合并。

第六步：合并，然后立刻同步

合并后这一步最容易忘，后果也最严重

忘了同步，你下次开分支就是基于过期的 main，PR 里会带上一堆无关改动，还会莫名冲突。养成肌肉记忆：

git switch main
git pull origin main
git branch -d feat/12-login-page   # 删掉本地分支
git fetch origin --prune          # 清理失效的远端分支引用

Review 时具体看什么

给一个可以直接照着走的顺序。前三步各一两分钟，但能挡掉八成的问题。

  1. 先看 CI。任何一个红叉都先别细读，先问为什么。

  2. 看改动范围。Files changed 超过十几个文件，或者改动几百行 → 直接要求拆小。一个 PR 只做一件事，这是最有效的 review 建议。

  3. 看有没有动不该动的文件：CI 配置、测试文件、锁文件（package-lock.json）、被压缩过的文件。这一步现在格外重要——见上面「CI 作弊」。

  4. 安全检查（优先级最高）。搜一下 diff 里有没有 password、token、secret、api_key、.env。有没有把用户输入直接拼进 SQL、命令行或文件路径。

  5. 真的跑一遍。reviewer 有责任真的把它跑起来，而不是只看 diff。跑不起来就说跑不起来，这本身就是重要信息。

  6. 兼容性。改没改接口、数据库字段、函数签名、依赖大版本？这几项最容易出事，而且本地看不出来。

两个人同时改会怎样

先说结论让你放心：如果你们在不同分支上改，Git 通常能自动合并。只有改到同一个文件的同一块区域时才会冲突。

情况结果
改不同文件毫无问题
同一文件、不同区域自动合并成功
同一文件的同一行冲突，需要你决定
两个人都直接改 main后 push 的人被拒绝——这是 Git 在保护你

最后那种情况的正确处理：

git pull --rebase origin main
git push

冲突怎么解决

rebase 时冲突，Git 会在文件里插入这样的标记：

<<<<<<< HEAD
（你这边现在有的内容）
=======
（远端同步过来的内容）
>>>>>>> origin/main

处理步骤：

  1. git status —— 看 Unmerged paths 那一段，那里列的就是冲突文件

  2. 打开冲突文件，把三个标记行全部删掉，只留下你要的内容（可能两边都要，手工组合）

  3. git add . 标记为已解决

  4. git rebase --continue（如果是 merge 冲突，这里是 git commit）

  5. 重新跑一遍测试，再 push

想放弃这次操作回到之前的状态：git rebase --abort 或 git merge --abort。

最后一步千万别省。冲突标记漏删一个，代码会语法报错；更常见的是语法没错但逻辑错了——两边的 CSS 合并后样式打架，两边的判断条件合并后互相覆盖。

怎么从源头减少冲突

  • 一个 PR 只做一件事。改 20 行的 PR 和改 500 行的 PR，冲突概率差 20 倍。
  • 重构单独开 PR，不要和功能改动混在一起。
  • 锁文件（package-lock.json 等）单独一个 PR，不要和代码混在一起——这是冲突重灾区。
  • 格式化交给工具统一处理（Prettier 等），自动格式化产生的改动集中在一个提交里，不会和别人的逻辑改动打架。

合并方式怎么选

方式结果什么时候用
Merge commit保留全部提交，加一个合并点需要保留完整历史时
Squash 合并压成一个提交，历史线性绝大多数团队，包括学生团队
Rebase 合并逐个提交放到主线，线性你们能保证每个提交都是有意义的原子提交

推荐 Squash 合并：历史干净、主干上的提交信息完全可控、PR 里的细碎提交（「改个错别字」「处理 review 意见」）不会污染主干。

用 squash 有一个配套规则必须知道

squash 合并之后，永远不要再用旧分支开新 PR。因为提交被压过了，共同祖先没变，后续 PR 会把已经合进去的改动再带一遍，于是你就得解决一遍一模一样、但看起来毫不相关的冲突。每次开新分支都从最新的 main 开始。

常见事故与处理

一、force push 覆盖了同事的提交

第一步：立刻停手，不要再 push 任何东西到那个分支。然后让同事在他自己电脑上执行 git reflog——它会列出所有历史位置，包括被覆盖前的提交。找到那个 SHA 后恢复：

git switch -c 分支名-recovered a1b2c3d
git push -u origin 分支名-recovered

预防比恢复重要：只用 --force-with-lease；分支保护里保持「Allow force pushes」关闭；永远不要 force push 到 main。

二、密钥泄露

这是所有事故里最紧急的一个。处理顺序很重要：先轮换，再撤销——

  1. 立刻去服务商后台创建新密钥
  2. 把所有用到旧密钥的地方（服务器、CI 密钥、本地配置）换成新的，并验证能跑通
  3. 然后才撤销旧密钥
  4. 用 git filter-repo 清掉历史里的密钥（改写历史是破坏性操作，必须先通知所有协作者）

只删文件是不够的——密钥会传播到 fork、备份和 CI 日志里，删掉文件不等于密钥消失，必须撤销。

预防：所有密钥放 .env（进 .gitignore），仓库里只提交一个 .env.example 放变量名。GitHub 对公开仓库的 secret scanning 推送保护是免费且已正式可用的——它会在你 push 时直接拦下疑似密钥。

三、误删分支

如果这个分支曾经开过 PR：仓库 → Pull requests → Closed → 找到对应的 PR → 页面底部点 Restore branch。或者用 git branch 分支名 <sha> 从某个提交重建。

没开过 PR 的分支恢复就没有保证了。预防：分支保护里把「Allow deletions」保持关闭。

四、想撤销一个已经合并的提交

用 git revert <提交>，不要用 reset。revert 会生成一个「反向提交」，历史完整保留——这在协作场景是必需的，因为你需要能证明「曾经有过这个问题，后来被撤销了」。GitHub 网页上那个 PR 底部也有 Revert 按钮。

如果只记住五句话

  1. 合并后立刻同步：git switch main && git pull && git branch -d <分支>。这一步忘了，后面全是无谓的冲突。

  2. 只用自己的分支 rebase，只用 --force-with-lease。

  3. 一个 PR 只做一件事。这是降低冲突和 review 成本的最大杠杆。

  4. 项目第一天就配好分支保护和 CI。它不是「以后有空再说」的事，是让错误难以发生的前提。

  5. main 永远只走 PR。包括你自己。

写在最后HOW TO VIBE WELL

怎么成为一个
好的 vibe coder。

Vibe coding 这个词来自 Karpathy 在 2025 年 2 月的一条推文。他的原话值得完整看一遍，因为很多人只记住了前半句。

「我完全跟着感觉走，拥抱指数增长，甚至忘了代码的存在。我永远点 Accept All，已经不看 diff 了。代码增长到了我理解不了的程度……对于扔掉也无所谓的周末项目来说，这不算太糟。」

注意最后半句：提出这个词的人，一开始就说了它不适合正经项目。而且他描述的本来就是一个失控状态——代码超出自己的理解范围。

所以真正的问题不是「要不要 vibe coding」，而是：怎么用它的速度，同时不落到「代码没人能维护」的地步。

独立研究者 Simon Willison 给了一条非常实用的标准：

如果我不能向别人准确解释这段代码在做什么，我就不会把它提交进我的仓库。

这不是说新手必须看懂每一行——那不现实。而是说你得知道它在做什么、能回退、出了错能修。达不到这个标准之前，把代码当成草稿，别当成产品。

风险是真实存在的，不只是理论担忧

一项对 200 个已上线应用的安全审计（arXiv:2606.23130）发现：91% 至少含一个漏洞，其中三分之二属于严重或高危级别，集中在访问控制失效、注入和认证缺失。另一项 186 个真实任务的基准测试（arXiv:2512.03262）发现：功能正确的方案里有 57%，但安全的只有 11.8%。

结论不是「别用 AI 写代码」，而是：功能跑通不等于可以上线。

下面这六条，是把前面六章压缩之后留下的部分。刚开始做的时候，先照着做，做熟了再慢慢内化成习惯。

01

用 AI 提速度，不用它替你负责

它可以写得很快，但出了事是你在承担。「先跑起来」阶段可以不看每一行；「要给用户用」阶段必须能解释、能验证。

02

先看计划，再让它动手

一句「先别写，给个方案」能省掉大量返工。看不懂的计划不该被执行。

03

每个任务前后都留检查点

用 Git 存档。这是 AI 时代最该先学会的习惯——它让「大胆试」这件事变得安全。

04

规则写进 AGENTS.md，别靠记忆

人和 AI 都需要一份长期说明书。团队里这份文件本身就是最好的新人文档。

05

让它自证，而不是你信它

别停在「它说写好了」。要求它跑测试、跑起来给你看、检查 diff。功能正确和安全是两件事。

06

代码最终要交给人

GitHub 仓库是这个工作里最重要的资产。它让任何人（包括三个月后的你）能看懂、改得动、接得下去。
